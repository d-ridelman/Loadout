# Исследование расхода токенов, лимитов и эффективности AI-агентов

<p><a href="RESEARCH.md">English</a> | <strong>Русский</strong></p>

В документе сведены три проверки: схема роутинга из X (`@0xCodila`, 10-11.11.2026) и документации Anthropic, разбор идеи «Rust MCP + PostToolUse-демон» из обсуждения с Gemini и замер 30 реальных сессий Claude Code (`26 256` ходов ассистента через [`scripts/audit-sessions.mjs`](../scripts/audit-sessions.mjs)).

## Где работает экономия

`ctxkit` написан на Rust только ради нативного exe со стартом `9-14 ms` без поднятия Node или Python на каждый вызов. Сама экономия относится к любым проектам, включая TypeScript/JS, Python и Go: в измеренных 30 сессиях основная потеря контекста пришлась на `2 793` shell-инспекций и `1 363` полных чтения файлов размером до `66.6 KB`, а также `2 197` запусков `tsc`, `npm test`, `node --test`, `pytest` и сборок.

## Выводы из X (`@0xCodila`) и документации Anthropic

Посты `@0xCodila` описывают 4-модельную команду и заявляют снижение расхода до `~3.4x` по сравнению с работой флагманской модели на каждом шаге. Роли совпадают с документацией Anthropic (`advisor`, `advisor-tool`, `sub-agents`, `model-config`), но цифры `~3.4x` на этих страницах нет (сверка 15.11.2026): считать заявлением автора, а не замером. В документации сказано лишь, что быстрая основная модель с сильным советником «typically costs less», чем сильная модель на всех ходах.

| Роль | Модель | Инструменты и задача | Зачем нужна в схеме |
|---|---|---|---|
| Основная сессия | `Sonnet` (`sonnet`) | Пишет код, правит файлы, запускает тесты | Основной объём ходов на быстрой средней модели |
| Советник | `Fable` (`advisorModel: fable`) | Только отвечает на консультации | Вызывается около 3 раз за задачу: план, повтор ошибки, финал |
| Поиск и чтение | `Haiku` (`Explore`) | `Read, Grep, Glob` (read-only) | Удерживает большой поиск вне кэша основной сессии |
| Финальный ревьюер | `Opus` (`checker`) | `Read, Grep, Glob, Bash` (read-only) | Проверяет `git diff`, прогоняет тесты и краевые случаи перед сдачей |

При проверке документации и практики выявились четыре технические детали, без которых роутинг ломается:

1. Автор заявляет, что в тестах Anthropic без явной инструкции в `CLAUDE.md` (вызывать advisor перед фиксацией подхода, при повторе той же ошибки дважды и перед финалом) Sonnet обращался к advisor `0 раз из 198`. Этой цифры на страницах Anthropic нет (сверка 15.11.2026). Страница advisor tool говорит только, что без подсказки в системном промпте исполнитель «tends to under-call the advisor», особенно на задачах с кодом, а моменты вызова модель выбирает сама: настройки, которая принуждает к вызову или ограничивает его, нет. Поэтому и нужны блок в `CLAUDE.md` и шлюз Stop.
2. Автор заявляет, что снижение `effortLevel` у основной модели резко сокращает вызовы advisor. Документация этого не подтверждает. Она говорит, что Sonnet 5.5 по умолчанию работает на `medium`, что Sonnet на `medium` с советником сопоставим с Sonnet на стандартном effort при меньшей цене, а для максимума исполнителю лучше оставить стандартный effort. Значит, `effortLevel: high` в `ctxkit setup` — наш выбор, а не требование документации: сравнить `medium` и `high` через `ctxkit report` (вызовы advisor по дням, доля ходов Sonnet). К тому же по settings-reference верхнеуровневый `effortLevel` в пользовательском `~/.claude/settings.json` игнорируют Opus 5.5 и «модели, вышедшие после него»; Sonnet 5.5 страница не называет, но живая проверка (15.11.2026, Claude Code 2.1.325, изолированный `CLAUDE_CONFIG_DIR`, `--setting-sources user`, `claude -p` через локальный прокси, который логирует `output_config.effort` из тела запроса к API; `/effort` и init-сообщение stream-json уровень не показывают) подтвердила: верхнеуровневый `effortLevel` в user-настройках на `sonnet` (`claude-sonnet-5-5`) **не действует** (`low` и `high` отправляют то же `medium`, что и без настроек), а `modelSettings["claude-sonnet-5-5"].effortLevel` действует (`low` даёт `low`, `high` даёт `high`) и побеждает верхнеуровневый ключ при конфликте. Тем же способом проверено, что `CLAUDE_CODE_EFFORT_LEVEL`, `--effort` и верхнеуровневый `effortLevel` в файле `--settings` действуют. Документированные способы: `modelSettings` (`claude-sonnet-5-5`, v2.1.251+), `/effort` и `CLAUDE_CODE_EFFORT_LEVEL`; `ctxkit setup` теперь пишет `modelSettings` для основной модели (верхнеуровневый ключ остаётся для старых моделей) и не пишет `CLAUDE_CODE_SUBAGENT_MODEL` без `--subagent` (`doctor` предупреждает об оставшемся `haiku`).
3. Встроенный субагент `Explore` игнорирует переменную `CLAUDE_CODE_SUBAGENT_MODEL` и работает на основной модели. Нужно явно создать `~/.claude/agents/Explore.md` с `name: Explore` и `model: haiku`.
4. Корневой `CLAUDE.md` стоит держать короче 200 строк (~4-6 KB), вынося правила подпапок в `.claude/rules/*.md` с полем `paths:`. Исключения из запрета, написанные в том же предложении, повышали соблюдение правил в замерах Anthropic с `~1/10` до `~9/10` (заявление из тех же публикаций, источник не проверен).

Сверено с полным текстом страниц (15.11.2026): советник читает весь транскрипт, и его собственное чтение не кешируется, поэтому цена растёт с длиной транскрипта; обычный ответ советника 400–700 токенов текста (1 400–1 800 с рассуждением), это главная статья расхода; на задачу с кодом ожидается два–три вызова; у каждой модели свой кеш промпта, так что `/model` посреди задачи перечитывает разговор без кеша, а переключение `/advisor` и смена effort на Sonnet 5.5 кеш сохраняют; на исполнителе Sonnet подсказка-напоминание в тексте заметного эффекта не дала, а на Opus слегка снизила результат. Настройки только для API: `caching` советника окупается примерно с трёх вызовов, `max_tokens: 2048` сократил ответ советника примерно в 7 раз (n = 40, разница точности в пределах шума).

Для оценки роли советника в статье приводились бенчмарки `Fable 5.2`: `Remote Labor Index` `41.3%` против `21.3%` у `Opus 5.5`, `20.8%` у `GPT-6 Astra` и `17.9%` у `Fable 5.1`; `BenchCAD 2.1` `83.5` против `65.3`; `OSWorld 2.1` `89.3%`. Бенчмарки и цена `$8` / `$40` за 1M input/output токенов взяты из статьи автора и не сверены со страницами Anthropic. При такой цене гонять такую модель на grep и чтение конфигов невыгодно, зато как редкий консультант она быстро окупается.

## Проверка идей из обсуждения с Gemini

В исходном обсуждении предлагалось отобрать у агента встроенные `Read`/`Bash` в пользу кастомного AST-MCP (`tree-sitter`/`syn`), повесить на `PostToolUse` демон с `cargo check` + `clippy --fix` + локальной LLM после каждой записи файла и запретить обычный текст в ответах через `CLAUDE.md`. Проверка показала смешанный результат.

| Идея из обсуждения | Решение | Основание |
|---|---|---|
| Сжатие `cargo check --message-format=json` и тестовых логов | Принято (`ctxkit check`) | Срезает `11.2%` мусора `tool_result` (реально ~6-10% общей экономии на разных стеках и до 12-15% при ошибках компиляции) |
| Неизменный префикс промпта под Prompt Caching | Принято | Инструмент `/advisor` сохраняет префиксный кэш, а смена модели посреди сессии его ломает |
| Срез `rendered.lines().take(4)` из примера кода | Исправлено | Суть ошибки Rust вроде `expected A, found B` часто уходит ниже 4-й строки `rendered`, поэтому `check.rs` читает `message.message` и primary `span` из JSON |
| Заменить нативные `Read`/`Bash`/`Edit` на AST-MCP | Отклонено | Обучение и навыки агентов привязаны к встроенным инструментам; AST уже закрывают LSP-серверы, а кастомный MCP ломается на логах, конфигах и `git` |
| Тяжёлый `PostToolUse`-демон после каждой правки | Отклонено | При правке N связанных файлов первые N-1 временно не собираются и порождают ложные ошибки; автоправка за спиной агента ломает следующий `Edit` |
| Запретить обычный текст в ответах | Опровергнуто цифрами | Текстовые ответы в чат дают около `1%` всех исходящих токенов |

## Скрытые утечки в конфигурации и инфраструктуре

При аудите окружения обнаружились пять проблем вне исходного кода:

1. **Пресеты Claude Desktop (`ccd-session-presets.json`) перебивают `settings.json`**. Десктопный клиент хранит модель и уровень усилий для каждого проекта отдельно и может открывать новые сессии на Opus или Fable вопреки глобальным настройкам CLI.
2. **Четыре перекрывающихся слоя проверок**. Глобальные хуки на все события (`*`), regex `Stop`-хуки, проверяющие формулировки текста («сказал "не проверил"»), тяжёлые команды на каждом `Stop` и локальные `.githooks`. Regex-блокировка ответа не ловит реальных багов в коде, но заставляет модель трижды прогонять весь контекст ради перефразирования. Надёжнее держать в `PreToolUse`/`PostToolUse` только быстрые детерминированные проверки (`< 20 ms`), а тесты запускать перед сдачей или коммитом. Шлюз Stop из `ctxkit setup` — узкое исключение: он читает только факты из транскрипта (правки файлов с кодом за ход, вызов `checker` или advisor после последней правки), не запускает команды, не смотрит на текст ответа и блокирует один раз за ход (повтор пропускает `stop_hook_active`). Он нужен, потому что одних правил модель не выполняет: по данным самого поста, Sonnet без явной инструкции обращался к advisor `0` раз из `198`.
3. **Более 20 глобальных плагинов и OpenAPI-MCP**. Описания инструментов каждого активного плагина и десятков эндпоинтов OpenAPI-MCP загружаются в каждый запрос. Глобально имеет смысл оставлять базовые 5-8 инструментов, подключая остальные точечно в `.claude/settings.json` проекта.
4. **Старые git worktree (`.claude/worktrees/`)**. Десятки забытых рабочих копий замедляют поиск и индексацию, поэтому их стоит регулярно удалять через `git worktree prune`.
5. **Отсутствие проекции `toMcp` в своих MCP**. Отправка сырых REST/UI-ответов (иконки, кнопки, история из 40+ записей) с отступами быстро съедает контекст без пользы для решения задачи.

Для любого харнеса (Claude Code, Antigravity или собственного агента) эффективнее всего работает пятиуровневый стек: настройка моделей и короткого `CLAUDE.md` (`ctxkit setup`), детерминированный `PreToolUse`-предохранитель на чтение и поиск, сжатие логов сборок и MCP (`ctxkit check` и `toMcp`), короткие сессии через `/clear` с батчингом инструментов (`Read`/`Edit`, `browser_batch`, `browser_snapshot` с `interactive_only: true` и `viewport_only: true`), а в собственных харнесах дополнительно Context Folding: сворачивание старых `tool_result` старше 6-8 ходов в одну строку статуса `[cmd #N -> OK / err]`.
