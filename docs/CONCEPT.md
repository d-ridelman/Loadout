# Loadout — концепт

[English](CONCEPT.en.md) · [Русский](CONCEPT.md) — русский текст первичен, английский — его перевод.

> Что загружено в твоих агентов: плагины, MCP, скилы, хуки, агенты, правила. Один экран на все клиенты.

Статус: документ начинался как концепт до первой строки кода; разделы 1–9 и 11–12 в основном описывают исходный замысел и местами дополнены по ходу работ, а поправки, где замысел разошёлся с сделанным, помечены «позже». Приложение с тех пор сделано (версия 1.1.0): что готово и как проверено — §10, §13 и `README.md`. Кликабельный макет `mockup/index.html` — макет начального замысла, нынешний интерфейс он не показывает.
Метки в таблицах: **[проверено]** — видел на этой машине: имена файлов, каталогов и ключей, плюс по одной записи без секретов (`installed_plugins.json`, шапка одного `SKILL.md`); значения из конфигов с токенами не читал; **[гипотеза]** — не проверено, в M0 надо подтвердить на фикстурах.

## 1. Боль и цель

Сущности агента размазаны по шести клиентам и десяткам файлов в разных форматах (JSON, JSONC, TOML, YAML, каталоги с `SKILL.md`). Ответить на «где стоит glidehand и включён ли он в Codex?» можно только руками.

Цель: за один взгляд видеть, **что где установлено, включено и сломано**, и безопасно этим управлять.

Не цели (v1):
- Управление облачными коннекторами на уровне аккаунта (подключить/отключить в claude.ai или ChatGPT). Публичного API нет, подробности и что всё-таки можно сделать — §5.1.
- Установка плагинов из маркетплейсов. Это дело самих клиентов. (Позже: окно ставит плагины Claude Code запуском CLI `claude` и скилы из GitHub или папки; см. `README.md` и `SECURITY.md`.)
- macOS и Linux. Пути абстрагируем сразу, но тестируем и собираем Windows 11. WSL-проекты (в `config.toml` Codex есть `\\wsl.localhost\...`) — после v1.

## 2. Какие клиенты и что про них известно

**ChatGPT desktop и Codex — это одно приложение на этой машине.** В меню Пуск пункт «ChatGPT» запускает Store-пакет `OpenAI.Codex_…` (`app\ChatGPT.exe`, запущенные процессы называются `ChatGPT`) **[проверено: `Get-StartApps`, `Get-AppxPackage`, `Get-Process`]**. Рядом стоит сторонняя оболочка «Codex Web GPT» 5.0.8 (данные в `%APPDATA%\Codex Web GPT`, Electron); её форматы не разбирал и в v1 не поддерживаю. Важные наблюдения, из которых вырос дизайн:
1. **Один пакет — несколько клиентов.** Плагин `ai-playbook` несёт сразу `.claude-plugin`, `.codex-plugin` и `.antigravity-plugin` **[проверено]**. Значит, одна логическая сущность живёт в клиентах отдельными экземплярами. Главный экран строим как матрицу «сущность × клиенты».
   **Тип у экземпляров может различаться:** glidehand в Claude Code включён как плагин (`enabledPlugins`), а в Codex и Antigravity подключён как MCP-сервер **[проверено проверяющим по именам ключей]**. Поэтому `kind` — свойство экземпляра, а `logicalKey` строки группирует по имени между типами. Правила сопоставления («плагин X» ↔ «MCP X») — задача M0.
2. **Дубли и дрейф уже есть.** В `installed_plugins.json` `skill-creator@claude-plugins-official` записан дважды: область `user` и область `project` (с `projectPath`) **[проверено]**. Поле `version` в двух записях разное (короткие git-хеши) — видел на этой машине. Отдельно `skill-creator` стоит и в `~/.codex/skills`, и в `~/.codex/skills/.system`.
3. **Свалка бэкапов.** В `~/.codex` и `~/.gemini/config` лежит по ~20 чужих `*.bak`. Мы не добавляем туда ничего, у нас своё хранилище.
4. **Секреты рядом с настройками.** `~/.claude.json` содержит ключ `oauthAccount` **[проверено, имя ключа]**. Что MCP-конфиги держат токены в `env` — **[гипотеза]**, значения я не читал. Маскирование — требование, а не опция.

## 3. Единая модель

```
Entity {
  id            стабильный хеш(client, scope, kind, name, source.file)
  logicalKey    ключ для строки матрицы: имя пакета/сервера, нормализованное
  kind          plugin | mcp | skill | hook | agent | command | rule | marketplace | memory | connector
                (свойство экземпляра: glidehand — plugin в одном клиенте и mcp в другом)
  client        claude-code | claude-desktop | codex | antigravity | deepseek
  scope         user | project(путь) | plugin(origin) | builtin | cloud
  origin        { plugin?, marketplace?, file, pointer }   // pointer: JSON Pointer / TOML key / строка
  state         on | off | broken | shadowed | stale | unknown
  version       строка | gitCommitSha
  capabilities  { toggle, remove, edit, copyTo[] }          // что разрешено делать с этим экземпляром
  usage?        { lastSeen, count }                         // если клиент это пишет
  fingerprint   хеш содержимого (SKILL.md, манифест) для поиска «та же вещь в другом клиенте»
  masked        поля, которые скрыты
}
```

Состояния:

| state | смысл | как узнаём |
|---|---|---|
| `on` / `off` | включено / выключено клиентом | `enabledPlugins`, механизмы выключения MCP из §2, `[plugins.*] enabled`, … |
| `broken` | команда MCP не найдена, `installPath` не существует, хук ссылается на отсутствующий скрипт | `which` / `exists`, без запуска |
| `shadowed` | одноимённая сущность перекрыта другой областью | порядок слияния конкретного клиента |
| `stale` | версия/хеш расходятся с другими клиентами или маркетплейсом | сравнение `fingerprint`/`version` |
| `unknown` | формат не распознан | адаптер сохраняет сырой фрагмент и **не трогает** |

Правило адаптеров: **неизвестные ключи сохраняем при записи как есть.** Форматы неофициальные и меняются, поэтому у каждого адаптера есть `schemaVersion`, а на любую неожиданность он отвечает `unknown`, а не падением.

## 4. Экраны

В макете (`mockup/index.html`) работают пункты 1–5 и 7; Журнал (6) — заглушка.

1. **Матрица (главный экран).** Строки — логические сущности, столбцы — клиенты, в ячейке — глиф состояния. Видно сразу: glidehand есть как плагин в Claude Code и как MCP в Codex, Antigravity и DeepSeek (запись `mcp-glidehand` в `cordis.patch.yml`). Фильтры по типу и состоянию, поиск, группировка по происхождению (плагин/маркетплейс). Строка раскрывается в экземпляры по областям.
2. **Радар.** Обзор: кольцо на клиент с числом сущностей по типам, пульс «здоров / есть проблемы», список проблем справа. Это «HUD»-экран, но не просто украшение: клик по сектору ведёт в матрицу с готовым фильтром.
3. **Инспектор (правая панель).** Источник (файл и строка/путь ключа), сырой фрагмент с маскированием, что произойдёт при изменении (diff до записи), кнопки «открыть в редакторе», «показать в папке», «копировать путь».
4. **Хуки: конвейер.** Жизненный цикл `SessionStart → UserPromptSubmit → PreToolUse → PermissionRequest → PostToolUse → Stop` по дорожкам клиентов; на каждом шаге — хуки в порядке выполнения, с matcher и источником (user / project / плагин). События разных клиентов сопоставляются по таблице соответствия, непарные помечаются.

   Таблица соответствия событий (что известно сейчас):

   | Клиент | События | Статус |
   |---|---|---|
   | Codex | `SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, SubagentStart, SubagentStop, Stop, Interrupt` | проверено (`~/.codex/hooks.json`) |
   | Claude Code | в `settings.json` сейчас используются `SessionStart, PreToolUse, PostToolUse, Stop` (`Stop` — шлюз Инструментов контекста, один раз за ход возвращает к `checker`/advisor); полный набор событий клиента не проверен | частично |
   | Antigravity | схема `~/.gemini/config/hooks.json` не разобрана | гипотеза |
   | DeepSeek | `PreToolUse`, `PostToolUse` (файл `context-toolkit-hooks.json`, формат как у Claude Code); других событий в нём нет, полный набор клиента не проверен | частично |
   | Claude Desktop (чат) | хуков на диске не найдено | не найдено |

   Шкала в макете (дорожки, штриховка «нет события») — иллюстрация формы, не данные.
5. **Доктор.** Автоматические находки: битые пути, дубли, перекрытия, расхождение версий, MCP с секретом в открытом виде, осиротевшие маркетплейсы, свалка `*.bak`. Каждая находка — «что, почему плохо, что предлагаем» и ссылка на сущность.
6. **Журнал.** Снимки состояния и diff «что изменилось с прошлого раза», откат. Появляется с M3 (в макете — заглушка).
7. **Палитра команд (`Ctrl+K`).** Переход к сущности, смена фильтра, действия над выбранным. Всё доступно с клавиатуры: `j/k` — строки, `h/l` — клиенты, `/` — поиск, `Space` — переключить (когда включена запись), `Enter` — инспектор, `?` — шпаргалка.

### Профили (M4)
Именованные наборы «что должно быть включено» (например, «рабочий Visiology», «реверс»). Применение профиля — это пакет записей через тот же безопасный конвейер, одним предпросмотром.

## 5. Безопасность записи

Читать можно всё, писать — по уровням. Уровень включается в настройках, по умолчанию выключен.

| Уровень | Что разрешено | Версия |
|---|---|---|
| R0 | только чтение | v1 / M1 |
| R1 | включить / выключить по флагу (плагины, коннекторы, записи Codex); у MCP без флага выключение — вынос в корзину, это R2 | M3 |
| R2 | править, копировать между клиентами, переносить в корзину, применять профили и встроенные Инструменты контекста | M4, §10.8 |

Конвейер любой записи:
1. **План**: ядро строит набор правок и diff, ничего не пишет.
2. **Предпросмотр**: UI показывает diff по каждому файлу, пользователь подтверждает.
3. **Клиент запущен?** Проверяем процесс (Claude Code, Codex, Antigravity, dsh). Если да — предупреждение, что клиент может перезаписать файл своим состоянием, и предложение подождать.
4. **Оптимистичная блокировка**: хеш файла до плана и перед записью. Не совпал — план перестроить.
5. **Бэкап** в `%APPDATA%\loadout-app\backups\<время>\` с манифестом (исходный путь, SHA-256). Чужие `.bak` не создаём.
6. **Атомарная запись**: временный файл рядом + переименование. TOML правим через `toml_edit` (сохраняет комментарии и порядок), JSON — точечной правкой по CST, а не перезаписью всего файла.
7. **Проверка**: перечитать и убедиться, что результат равен «исходник + план», остальное не изменилось.
8. **Откат** из журнала: та же карточка предпросмотра (файл, ключ, было → станет) и подтверждение. Удаление = перенос в корзину Loadout, не `rm`; при возврате JSON-запись встаёт перед тем ключом, что шёл за ней при выносе (если его уже нет — в конец объекта).

Через журнал проходят и откатываются из него: включение и выключение, корзина, правка и копирование MCP, добавление MCP, пакеты профилей и установка скилов. Не через журнал: установка плагинов и маркетплейсов Claude Code (её делает сам `claude`; плагин выключается в матрице, удаляется `claude plugin uninstall`) и Инструменты контекста (у них свой предпросмотр и свой откат, §13).

Секреты:
- Ядро по умолчанию отдаёт значения **замаскированными**. Значения `env` и заголовков MCP не выводятся вообще, только имена ключей; файлы из строки «Секреты других клиентов» в §2 не читаются. Аргументы и команды хуков — свободный текст. Два аудита подряд находили новые обходы у чёрного списка (по слову, по форме), поэтому подход обратный, **белый список**: в выводе остаётся только то, что опознано как безвредное, всё остальное заменено на `<masked>`. Показываются: имена флагов (`--port`, `-y`, параметры PowerShell из короткого списка), числа до пяти цифр, пути (укоренённые или оканчивающиеся именем файла известного типа, без `@ ? = ; & | + ! *`, двоеточие только в `C:`, ни один сегмент не похож на секрет: так строка base64 со слэшами не сойдёт за путь), URL (известная схема, проверенные хост и порт, без userinfo вида `user:pass@` и `токен@`, query, `;параметров`, токеноподобных, JWT и %-закодированных сегментов пути), имена пакетов с версией (`rea-agents@6.8.0`) и имя пакета после `npx`/`uvx`, имена файлов известных типов, исполняемый файл в позиции команды (только строчными буквами), небольшой набор типичных слов (`node`, `bash`, `mcp`, `serve` …) и операторы с перенаправлениями. Скрыты всегда: значение после секретно названного флага (`--token`, `--auth`, `--pat` …), `ИМЯ=значение`, JSON и хеш-таблицы PowerShell в аргументе, `-pПАРОЛЬ`, `/P:…`, неизвестные короткие флаги. Вложенные командные строки (`bash -c "…"`) разбираются рекурсивно до трёх уровней, кавычки учитываются, включая `\"`. Метка и `logicalKey` хука строятся из уже замаскированных токенов, а `type`, `timeout`, `matcher`, версии, хеши, имена скилов и событий хуков, область плагина и имена ключей `env` проходят фильтры по алфавиту и виду (слова, похожие на токен, отбрасываются); `description` скила проходит маскирование токеноподобных слов. Из всех строковых полей, включая указатели и имена, вычищается путь домашнего каталога (без учёта регистра и на границе слова; формы `C:\…`, `C:\\…`, `C:/…`, `/c/…`, `/mnt/c/…`, `/home/<имя>`, `\\localhost\c$\…`). Цена: часть полезного текста (позиционные слова, значения флагов) показывается как `<masked>`; полную команду UI покажет только по явному действию. Известные пределы: секрет в описании скила, который не похож на токен (обычная фраза), не маскируется; короткое имя 8.3 вычисляется по шаблону (первые шесть символов и `~1..3`), а не по файловой системе; в `args` MCP слово из списка безвредных слов (`debug`, `main` …) после секретного флага всё равно скрыто, но после *несекретного* показано.
- Копии и корзина — исключение из маскирования: **бэкап `before` и запись корзины хранят файл клиента целиком, открытым текстом, включая значения `env` MCP**. Они нужны для точного отката, замаскированная копия его не даст. Лежат в `%APPDATA%\loadout-app\backups` (`userData` Electron называется по `name` из `package.json`, `productName` лежит только внутри `build`, а в `app.asar` его нет; сверено по содержимому `app.asar` и по каталогу `%APPDATA%\loadout-app` на машине разработчика, упакованное приложение для этого не запускалось); отдельных прав Loadout не ставит, каталог наследует доступ профиля пользователя Windows (на Windows это сам пользователь, SYSTEM и администраторы). Хранение ограничено (`write/retention.rs`, константы `KEEP_OPS = 100`, `KEEP_DAYS = 90`): остаются последние 100 операций не старше 90 дней, возраст и порядок берутся из имени каталога `<мс>-<nn>`, манифесты для этого не читаются. Старые каталоги удаляются перед новой записью (для пакета и отката пакета — один раз на пакет; не удаляется всё, что не старше защищённой операции, пакет профиля не режется посередине, а полная копия скила после неполного отката уходит только по сроку), кнопкой «Очистить старые копии» в журнале (подтверждение в отдельном окне главного процесса, `app/src/main/confirm.ts`) и командой `loadout prune [--backups КАТАЛОГ]`. Метка `pruned` хранит id последней удалённой операции: откат такой операции отвечает «копия удалена очисткой», а не «не найдена». Корзина (`trash/`) не чистится: это единственная копия вынесенной записи, то есть живое состояние. Журнал разбирает только 200 последних операций, откат читает манифесты не старше нужной операции, а не все. Об этом прямым текстом сказано в диалоге включения R1/R2 (`app/src/shared/backups.ts`; тест ядра сверяет числа) и в README. NSIS оставляет данные при удалении (`deleteAppDataOnUninstall: false`: булев флаг, вопроса при удалении у electron-builder нет), как удалить вручную — в README.
- «Показать» — по удержанию, значение живёт в UI только пока удержано.
- Ни телеметрии. Приложение работает офлайн; само оно обращается в сеть только за проверкой обновлений на GitHub (по умолчанию включена, выключается галочкой; в запросах ничего о пользователе и его конфигах, §10.10). Остальная сеть — только при явной установке: плагин и маркетплейс ставит CLI `claude`, скил из GitHub — `git clone` (добавлено позже, подробности в `SECURITY.md`).

Запуск чужих команд:
- Проверка MCP («поднять и спросить tools/list») **выполняет команду из конфига**, поэтому только по явной кнопке на конкретном сервере, с таймаутом 5 с и в отдельном процессе. Массовой проверки нет. (Не сделано: см. §10.3 и §10.4.)

Claude Code: `~/.claude.json` → `claudeAiMcpEverConnected` — список имён вида `claude.ai Github` (у меня три: Claude Docs, Atlassian, Github) **[проверено]**. ## 6. Архитектура

```
┌────────────────────────── Electron ──────────────────────────┐
│ renderer (React + TypeScript + Vite)   — только UI            │
│   ▲ typed IPC (contextBridge, allow-list)                     │
│ main  — окна, меню, трей, файловые диалоги, сторож процессов  │
│   ▲ stdio: JSON-RPC, строки через \n                          │
└───┼───────────────────────────────────────────────────────────┘
    ▼
loadoutd (Rust, sidecar)  ──  loadout-core (библиотека)
   adapters/{claude_code, claude_desktop, codex, antigravity, deepseek}
   model · scan · diff · plan · backup · mask · watch (notify)
```

**Граница Rust ↔ Electron: sidecar по stdio, а не napi-rs.** Причины: падение парсера не роняет окно; не надо пересобирать нативный модуль под каждую версию Electron; тот же бинарь работает как CLI (`loadout scan --json`) и в тестах. Цена — сериализация, но объёмы здесь сотни записей, это не узкое место.

Выбор технологий (не из требований, а из удобства):
- Renderer: React + TypeScript, `@tanstack/react-virtual` для списков, Zustand для состояния. Ничего тяжелее. (Позже: обошлось без них, на деле React + TypeScript без библиотеки состояния и без виртуализации списков.)
- Rust: `serde`/`serde_json`, `toml_edit`, `serde_yaml` (YAML в v1 только чтение), `notify`, `rayon`, `sha2`, `jsonc-parser`. (Позже: на деле `serde`/`serde_json`, `toml` и `toml_edit`, `yaml-rust2` вместо `serde_yaml` (YAML и пишется, точечно по строкам), `jsonc-parser`, `sha2`, `notify`; без `rayon`. У Инструментов контекста свои `regex`, `serde`, `serde_json`.)
- Третий язык не нужен. Python/Go не добавляем.
- Упаковка: `electron-builder`, NSIS-установщик для Windows. Sidecar лежит рядом, путь зашит, не из PATH.

Безопасность Electron: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, строгий CSP без `unsafe-eval`, никаких удалённых URL, IPC только по allow-list, имена файлов из UI проверяются ядром (запись только в известные пути адаптеров).

Один экземпляр: `app.requestSingleInstanceLock()` вызывается после `setPath('userData')`, второй запуск выводит первое окно вперёд (`second-instance`) и выходит сам. Замок Electron привязан к каталогу `userData` (проверено на двух процессах Electron: разные `userData` через `setPath` и через `--user-data-dir` оба получают замок, один и тот же — только первый), поэтому проверочные прогоны со своим профилем (`LOADOUT_USER_DATA`, `--user-data-dir` у `pack-check`) не мешают друг другу и установленной копии.

Структура репозитория (позже: заменена на нынешнюю, в концепте была без `context-toolkit`, `shared`, `e2e`, `screenshots` и `state`):
```
Loadout/
  crates/loadout-core/     модель, адаптеры, диф, бэкап, конвейер записи, сторож
  crates/loadoutd/         бинарь loadout: CLI (scan, prune) и sidecar (serve, JSON-RPC)
  crates/context-toolkit/  Инструменты контекста (§13)
  app/src/{main,preload,renderer,shared}/, app/e2e/
  fixtures/                синтетические конфиги по форме реальных (снимки с живой машины не храним: там секреты и имена)
  docs/CONCEPT.md, docs/CONCEPT.en.md, docs/screenshots/
  mockup/index.html        макет начального замысла
  state/                   снимки окна из e2e
```

## 7. Производительность

Цели, **не измерены** (замерить в M1). (Позже: замеры скана — §10.2, простоя и памяти — §10.6.)
- холодный скан всех клиентов — меньше 500 мс на этой машине;
- простой — 0 % CPU, окно в фоне не перерисовывается;
- ОЗУ в простое — до 150 МБ.

Как достигаем:
- Скан параллельный (`rayon`), `SKILL.md` читаем только голову (до 4 КБ) для frontmatter.
- Кеш «путь + mtime + размер → разобранная сущность», перечитываем только изменившееся.
- Сторож `notify` только на известные конфиги и каталоги скилов. **Каталоги `plugins/cache`, `sessions`, `transcripts`, `projects`, `*.sqlite` не слушаем** — они огромные и шумные. Дебаунс 200 мс.
- Виртуализация списков, иначе матрица на тысячу строк тормозит.
- (Позже: `rayon`, кеш по mtime и виртуализация списков не сделаны, скан идёт без параллельности; замеры — §10.2 и §10.6.)
- Рендер матрицы без анимации на каждую ячейку.

Палитра (официальный Dracula):

| фон | `#282a36`, панели `#21222c`, линии `#44475a` |
| текст | `#f8f8f2` |
| приглушённый текст | **`#9aa5ce`**, не `#6272a4` |

**Контраст посчитан** (WCAG, формула из спецификации): классический «comment» `#6272a4` на `#282a36` даёт **3,03:1** — не проходит AA для текста (нужно 4,5). Для текста берём `#9aa5ce` (5,86:1). `#6272a4` годится только для рамок и декора. Красный `#ff5555` на фоне — 4,53:1, проходит впритык, поэтому красный всегда с глифом и подписью.

HUD-эффекты — только то, что дёшево:
- уголки-скобки на панелях (псевдоэлементы); сканлайнов (линейной горизонтальной ряби поверх окна) и мерцания логотипа **нет**: убраны в M4 по замечанию владельца, на скриншотах штриховка читалась как рябь;
- свечение акцентов через `box-shadow` / `text-shadow`;
- радар с вращающимся лучом (`conic-gradient` + `transform: rotate`, идёт на композиторе, не вызывает layout);
- пульс состояния (`opacity`), короткая «загрузочная» анимация при запуске (до 600 мс), счётчики с плавным набором чисел;
- никакого WebGL/canvas в v1. Это вопрос расхода GPU на общей машине.

Управление эффектами: настройка **«Анимация»: выкл / лёгкие / полные** (Справка → Вид, палитра команд). При `prefers-reduced-motion` включается «выкл» сам. Если окно теряет фокус или свёрнуто, анимации ставятся на паузу.

Доступность: состояние не только цветом, но и формой глифа (`●` вкл, `○` выкл, `◐` расхождение, `◒` перекрыто, `☁` только облако, `✕` сломано, `–` нет); на фоне панели не используем `#44475a` как цвет текста или глифа (контраст около 1,7), для «нет» берём `#6272a4` только как декор рядом с подписью; видимое кольцо фокуса; матрица — `role="grid"`; полная работа с клавиатуры.

Шрифты: текст — системный Segoe UI 14 px (с хинтингом под ClearType; при масштабе 100 % и 125 % он на ~15 % чётче веб-Inter, замер в истории коммитов), JetBrains Mono **вшит в сборку** и только для кода, путей, клавиш и чисел, не мельче 12 px. Без CDN (офлайн). Мелкий и моноширинный текст в подписях ловит проверка окна (`typeCheck` в `app/e2e/run.mjs`).

## 9. Тесты

- Rust: у каждого адаптера golden-тесты на синтетических фикстурах (`fixtures/`), property-тест «записали → перечитали → равно исходнику плюс правка, неизвестные ключи целы».
- Тест маскирования: ни одно значение из списка секретных ключей не доходит до JSON-RPC-ответа.
- Electron: Playwright (`_electron`) — запуск, матрица видна, клавиатурная навигация, `prefers-reduced-motion`.
- Контраст: автотест на токены палитры (пороги 4,5 / 3).

Что гипотезы показали на реальных файлах:
- **`scope` у плагинов бывает не только `user` и `project`, но и `local`** (две записи). Это не штатный механизм Claude Code (по собственной заметке владельца, сервер возвращают переносом записи в `mcpServers`), но он годится как образец для корзины Loadout. Сканер показывает их как `off` и пропускает ключи с `_`.

А вот **сопоставление хуков между клиентами по метке на реальных данных не подтвердилось**: общих `logicalKey` нет. У Claude Code это `ctxkit` и `pull-skills`, у Codex все девять событий идут через один обёрточный скрипт `~/.orca/agent-hooks/codex-hook.cmd`. - **Один логический объект в разных клиентах** на живых данных работает: glidehand — плагин в Claude Code и MCP в Codex, harnio — плагин в обоих, `bash-tui` и ещё три скила есть в обоих.
- **Скилы:** Claude Code 16, Codex 32 (27 + 5 из `.system`), как и нашёл checker.

Что M0 поймал в самом себе, в два захода:
1. Прогон на реальных конфигах (проверка «значения секретных ключей не встречаются в выводе») нашёл утечку: заголовок одним аргументом (`--header "Authorization: Bearer …"`) не маскировался.
2. Независимый аудит `checker` пробил маскирование ещё в десяти формах: `-e GH_PAT=…`, `--env ИМЯ значение`, `curl -u user:pass`, JSON в аргументе, `-H Имя:значение` без пробела, `--auth`, строка подключения `Password=…`, ключ в пути URL, `OAUTH_…`, `--pat`. Хуже того, секрет попадал в **имя хука и `logicalKey`**, потому что метка строилась из сырой команды, а `mask_line` резал строку по пробелам и не знал про кавычки. Первое исправление — токенизатор с кавычками и правила по форме и виду значения, метка хука из замаскированных токенов. Двенадцать форм аудита и случаи с кавычками вошли в тесты (оговорка: ключ в пути URL в тесте длиной 30 символов, короткий ключ в пути, до 24 символов, не маскируется). Повторный проход нашёл ещё обходы: вложенная командная строка одним аргументом (`bash -c "tool --token X"`, в том числе с `;` и `=`), секрет с пробелом (`--token="a b"`) в метке хука, позиционные пароли (`mysql -pX`), JSON внутри аргумента, пароли в URL с `?`, `#`, `/`, путь дома в виде `C:\\Users` внутри JSON, UNC-путь. Каждый такой ответ чёрным списком был бы очередной заплаткой, поэтому маскирование **переписано как белый список** (§5). Заодно тест на кириллицу поймал в самом `scrub` панику: срез строки по байтовому смещению внутри буквы (исправлено).

Третий аудит (уже по белому списку) всё равно нашёл обходы: токен в userinfo URL без двоеточия (`git+https://ghp_…@github.com/…`), вложенная строка, у которой первое слово — путь (`bash -c "/usr/bin/tool секрет"`), base64 со слэшами, принятый за путь, схема и хост URL без проверки, значения после несекретных флагов (`-p`, `--passphrase`), редиректы (`2>/dev/null секрет`), поля вне `mask.rs` (имена, описания, область, ключи `env`), смешанные разделители и короткие имена 8.3 в пути дома. Всё закрыто в коде и тестах; на реальных данных белый список теперь показывает больше полезного (имена пакетов после `npx`, пути скриптов), чем показывала вторая версия, а `<masked>` в выводе осталось 3. Четвёртый аудит не запускался: гарантии «обходов нет» нет, это трижды проверенная и каждый раз пробиваемая защита, поэтому в M1 нужен фаззинг и список запрещённых форм из аудитов в CI. Заодно вычищается путь домашнего каталога из всех строковых полей, включая указатели, без учёта регистра и в формах Git Bash, WSL, `/home/<имя>`.

После правок из 23 проверенных на реальных конфигах секретных значений (теперь включая значения после секретных флагов в args) в выводе осталось одно, и это не секрет: URL `N8N_API_URL`, совпадающий с адресом самого сервера. Это проверка по конфигам этой машины, а не доказательство: список форм в тестах придуман по найденным обходам, и новые обходы возможны. Поэтому в M1 маскирование остаётся под фаззингом и аудитом.

Решения по замечаниям аудита: `stale` у плагина теперь только при разных версиях **внутри одной области**; другая версия в `project`/`local` даёт пометку, но не состояние (на реальных данных `stale` стало 0, раньше было 2). JSON Pointer теперь экранирует `~` и `/`, TOML-ключи в указателях единообразно в кавычках при необходимости. Не исправлено сознательно: пароль в URL с `/` внутри, потому что такой пароль по стандарту должен быть закодирован.

Обещанные к проверке в M0 пункты и что с ними: схема `dsh-mcp-client` (пакет недоступен, junction битая, §11), `deniedMcpServers` (в `settings.json` владельца ключа нет), секции `[apps.*]` в Codex (на машине их нет, официальную схему не читал) — всё три не проверено и перенесено на M1 (закрыты в M1, §10.2); место хранения переключателя `/mcp` — косвенно подтверждено (`projects.*.disabledMcpServers`, §2).

Намеренно не сделано в M0 (`shortcut:`): настройки проекта (`.claude/settings.json`, `settings.local.json`, `.mcp.json`), сущности, которые приносят сами плагины (их скилы, хуки, MCP), `skillOverrides`, `projects.*.disabledMcpServers`, сравнение дублей между областями (Доктор), символьные ссылки, пути длиннее лимита Windows. Сторож файлов и запись — M2 и M3.

### 10.2 Итоги M1 (приложение и пять клиентов)

Что есть: Rust-ядро читает **пять клиентов** (добавлены Claude Desktop, Antigravity, DeepSeek), Electron-приложение `app/` (electron-vite, React, TypeScript) запускает ядро командой `loadout scan --json` и показывает Матрицу, Радар, Хуки, Доктора, Палитру команд и Инспектор. Только чтение.

**Решение про sidecar.** В M1 `serve` (JSON-RPC по stdio) не нужен: полный скан занимает 55 мс, а сторож файлов — M2. Main-процесс делает `execFile` на бинарь по фиксированному пути, ответ проверяется по форме. `shortcut:` JSON-RPC и push-обновления добавляются вместе со сторожем.

**Агрегация строки и ячейки** (в макете её не было, на реальных данных она решающая). Строки группируются по классу, а не по `kind`: плагин и MCP одного имени — одна строка (`glidehand` — плагин в Claude Code, MCP в Codex, Antigravity и DeepSeek), маркетплейс того же имени — другая строка. В ячейке «клиент × строка» может быть много записей. Главная — по области: `user`, затем `local`, `plugin:*`, `profile:*`, `builtin`, `project:*`, `cloud`; рядом счётчик `+N`. Так десятки project-записей плагина не перекрывают его user-запись. Строки, где все ячейки `unknown` (флаг включения лежит в настройках проекта), по умолчанию скрыты флажком; Доктор их считает. Хуки группируются по метке, а хуки-обёртки одной программы (`~/.orca/agent-hooks/codex-hook.cmd`, `dsh-hook.cmd`) — под общим ключом `orca-agent-hooks`. Девять событий Codex дают одну строку с девятью записями.

**Что нового выяснено на машине.**

- Claude Desktop: в `claude_desktop_config.json` для сущностей только `mcpServers` (`preferences` — не сущности).
- DeepSeek: `cordis.patch.yml` читается парсером `yaml-rust2`, тег `!!js process.cwd()` не роняет разбор и не исполняется; профили (`profiles/<имя>/cordis.patch.yml`) читаются отдельно (в двух есть плагин `ponytail-dsh`); хуки идут через запись `dsh-hooks-*` → `configPath` (читается только внутри домашнего каталога, `..` отклоняется).

Флага `enabled`/`disabled` нет; запись плагина правится «на горячую»: по описанию пакета изменение записи отключает и заново подключает сервер без перезапуска хоста. Ключа `reconnect` из файла владельца в этой версии пакета нет: файл новее пакета.

- Скачивание `npm pack` пакета dsh показало, что пакет вызывает MCP-серверы напрямую (`command` из записи): это подтверждает, что `command`/`args` записей dsh нужно маскировать так же, как у остальных клиентов (маскируются через общий `mcp_detail`).

### 10.3 Итоги M2 (сторож файлов, постоянное ядро, Доктор)

Теперь тест имеет нижнюю границу (нет предупреждений, у каждого найденного клиента есть записи, `cordis.patch.yml` даёт MCP dsh, имена не скрыты). **Постоянное ядро.** `loadout serve [--home ПУТЬ]`: JSON-RPC по stdio, по одному сообщению в строке со сбросом буфера. Методы: `scan` (перечитывает диск), `snapshot` (последнее состояние), `status`; уведомления `ready` и `changed`. Методов с путями нет. В `changed` только id записей (`added`, `removed`, `changed`), признаки `warningsChanged`, `factsChanged` и порядковый номер `seq`; сырых путей и значений в событии нет, это проверяет тест. Битая (не UTF-8) строка на stdin получает ответ-ошибку, процесс не выходит. EOF на stdin завершает процесс за секунды (иначе на Windows ядро пережило бы окно). `loadout scan --json` работает как раньше.

**Сторож (`notify` 8.2, стабильный; `9.0.0-rc` не брали).** Каталоги слушаются нерекурсивно с фильтром по имени файла (замена файла переименованием рвёт наблюдение за самим файлом, за каталогом — нет); рекурсивно — только каталоги скилов. `plugins/cache` (кроме `openai-curated-remote` Codex: там записи — подкаталоги), `sessions`, `projects`, `*.sqlite`, `*.jsonl`, `node_modules` не слушаются; `*.bak*`, `*.backup`, `*.recovery` значимы только как прямые потомки четырёх каталогов клиентов (из них считаются факты Доктора). Набор путей пересобирается после каждого скана, даже без смысловых изменений: файлы, из которых собраны записи (например, динамический `configPath` хуков dsh), добавляют своих родителей. Каталог, созданный после запуска ядра (клиент поставили позже, `skills` появился), замечается: появление, удаление и переименование самого постоянного каталога значимо, а для каталога, которого ещё нет, слушается ближайший существующий предок (`.gemini` для `.gemini/config`, `AppData/Roaming` для Claude Desktop, иначе дом), и создание промежуточных каталогов тоже значимо. Подписка на удалённый каталог сбрасывается сразу, даже если его тут же создали заново с тем же содержимым (`git checkout`: скан тот же, `changed` нет, но старая подписка мертва); после любой ошибки сторожа пересоздаются все подписки. Debounce 300 мс, но не дольше 2 с при непрерывных событиях; срок проверяется в начале каждого шага, поэтому поток запросов не откладывает скан. Любая ошибка сторожа — повод перечитать диск. Каталог junction'ов dsh (`profiles/node_modules/@deepseek-ai`) не слушается: факт о битых ссылках обновится при следующем скане по любому другому событию или вручную. Главное: после debounce скан сравнивается с прошлым, и `changed` уходит **только при смысловом отличии**, поэтому постоянная перезапись `~/.claude.json` окно не мигает.

### 10.4 Итоги M3 (запись R1)

**Объём.** Переключаются только булевы флаги, которые уже есть в форматах клиентов: Claude Code — `enabledPlugins[ключ]` и `disableClaudeAiConnectors` (один ключ на все коннекторы сразу, в плане это показано числом затронутых записей); Codex — `plugins.*.enabled`, `mcp_servers.*.enabled`, `apps.*.enabled`. На машине владельца это 63 записи. Там, где «выключить» значит убрать или перенести запись (MCP в `~/.claude.json`, Antigravity, DeepSeek, Claude Desktop), переключателя нет, а инспектор пишет причину (поле `toggleWhy`): это корзина и правка, то есть M4.

**Как устроено.**
- Ядро (`write.rs`, `edit.rs`): запись → `target` (настоящий файл и сырой ключ, `#[serde(skip)]`, наружу не идёт). RPC принимает только id записи и желаемое состояние, ядро заново сканирует и находит цель само; методов с путями по-прежнему нет. Писать можно только в `~/.claude/settings.json` и `~/.codex/config.toml` (список проверяется и при записи, и при откате: манифест лежит в каталоге пользователя и не считается доверенным).
- Правка точечная: JSON — по AST `jsonc-parser`, меняется только литерал `true`/`false` (или добавляется одна запись с отступом файла), TOML — `toml_edit` 0.22 (та же копия, что у `toml 0.8`), комментарии и порядок целы; BOM и CRLF сохраняются, повтор ключа правится по последнему (так читает `serde_json`). В файле со смешанными CRLF/LF и в пустом объекте с комментарием правка отказывает.
- Конвейер (§5): хеш файла в плане → сверка при `apply` и ещё раз перед записью → бэкап (`before`) и манифест с `sync_all` → временный файл `…loadout.<pid>.tmp` рядом, сверка файла с планом ещё раз сразу перед `rename` (при расхождении замены нет) и `rename` → перечитать и сверить с планом. Откат — та же запись из бэкапа, только если хеш файла равен «после» из манифеста, иначе отказ. Каталог бэкапов приходит аргументом `serve --backups`; без него `apply`, `journal`, `rollback` отказывают (`plan` работает всегда).
- Предпросмотр содержит файл (с `~`), указатель, значения `было → стало`, затронутые записи; содержимого файла и контекстных строк нет (тест с `FAKE-SECRET`).
- Окно: уровень R0/R1 хранится в профиле приложения (по умолчанию R0) и проверяется в main перед каждым `apply`/`rollback`; повышение до R1 подтверждает диалог ОС (страница нажать его не может; с 1.1.0 вместо него отдельное окно, которое рисует и слушает main). Перед предпросмотром main через `tasklist` проверяет, запущен ли клиент (предупреждение, не запрет). Space на выбранной ячейке или кнопка в инспекторе → предпросмотр → «Применить»; раздел «Журнал» с откатом; `changed` приходит сразу после записи, не дожидаясь сторожа.

**Проверки.** Ядро: 12 интеграционных тестов записи на копии фикстур (туда и обратно побайтово, устаревший план, откат после чужой правки, вставка отсутствующего ключа, коннекторы с общим ключом, запрет по имени, цепочка откатов, `apps`, отсутствие содержимого и путей в ответах, подмена пути в манифесте) и 9 тестов `edit.rs`; три теста `serve` по JSON-RPC. ### 10.5 Итоги M4 (R2: корзина, правка, копирование, профили)

**Решение по корзине.** Вынесенная запись лежит в хранилище Loadout (`<бэкапы>/trash/<id>.json`), а не новым ключом в чужом файле: нигде не проверено, что Claude Desktop и Antigravity сохраняют незнакомые ключи при перезаписи, а потерянный ключ означал бы потерянную запись. В скане такая запись видна как `off` с прежними файлом и указателем, поэтому её id, выбор в окне, журнал и профили не меняются. «Включить» — прямая вставка сохранённого текста обратно. «Удалить» из §5 и есть вынос в корзину, отдельной операции удаления нет. Стэш владельца (`_disabledMcpServers` в `~/.claude.json`) включается переносом внутри файла; откат этого включения при неизменном файле возвращает файл из бэкапа (запись снова в стэше), а если файл с тех пор менялся, обратная операция выносит запись в корзину Loadout (в стэш она тогда не возвращается). У записи из стэша указатель меняется (`/mcpServers/x`), поэтому id после включения другой, и откат находит запись по клиенту, типу и имени.

**Что можно (уровень R2, кроме флагов).**
- Вынос и возврат MCP без флага «выключено»: Claude Code (`~/.claude.json`, область user), Claude Desktop, Antigravity (`mcp_config.json`) — по значению JSON, остальные байты файла те же (проверено: первая, средняя, последняя и единственная запись, CRLF, возврат даёт семантически равный файл); DeepSeek — по строкам `cordis.patch.yml` (§ ниже).
- Правка: `command` и `args` MCP целиком. Окно получает их только в замаскированном виде; ядро добавляет признак `exact`, когда маскирование ничего не изменило, и только тогда форма начинается с текущих значений (иначе поля пустые: замаскированная строка, сохранённая обратно, стёрла бы секрет). Новая команда и аргументы в предпросмотре и журнале идут через то же маскирование (`--token X` → `<masked>`), в файл попадают как введены; `env` и заголовки не меняются.
- Копирование MCP между Claude Code, Claude Desktop, Antigravity и Codex с переводом формата JSON ⇄ TOML (`headers` ⇄ `http_headers`, у Claude Code добавляется `type: http`). Значения `env` и заголовков (секреты) ходят только внутри ядра: RPC принимает id источника и клиента-получателя, в предпросмотре — имена ключей `env`, что не переносится, и замаскированная команда. Занятое имя (в файле или в корзине получателя) — отказ.
- Профили (`<бэкапы>/profiles.json`): имя, набор «клиент, тип, область, имя → включено/выключено». Создаются снимком текущего состояния плагинов и MCP (коннекторы не входят: один ключ на все), правятся флажками. Применение — пакет: один предпросмотр на все отличающиеся записи, у каждой свой бэкап и строка журнала с общим номером пакета, «Откатить пакет» откатывает всё с последней записи. Подпись пакета (хеши файлов) сверяется при применении, при первой ошибке пакет останавливается, сделанное остаётся в журнале.
- Откат вынесенных и возвращённых записей — обратная операция над текущим файлом (`~/.claude.json` клиент переписывает постоянно, сверка хеша там почти всегда отказывала бы); откат флагов, правок и копий — возврат файла из бэкапа при неизменном хеше «после».

**DeepSeek.** `cordis.patch.yml` нельзя разбирать и собирать заново (тег `!!js`, его пишут многие установщики), поэтому вынос и возврат идут по строкам (`yaml_edit.rs`): положение записи берётся из событий разбора `yaml-rust2` (строка начала каждой записи списка `insert`), вырезаются строки записи вместе с пустыми строками перед ней, строки-комментарии установщиков на нулевом отступе между операциями остаются на месте. После правки результат разбирается заново и сверяется: остальные записи равны прежним, у этой нет (или она на месте). Не сошлось, якоря, алиасы, потоковый стиль или табы — отказ, файл не меняется. Проверено: вынос и возврат побайтово на фикстуре (в том числе CRLF и файл без перевода строки в конце) и на **настоящем** файле без записи (сухой `plan`: структура файла с комментариями установщиков сначала не проходила проверку границ, это исправлено). Править и копировать запись DeepSeek нельзя.

**Уровни.** R0 — только чтение, R1 — флаги, R2 — корзина, правка, копирование, профили. Каждый включает прежние. Хранятся в профиле приложения, проверяются **и в main, и в ядре**: main передаёт ядру `maxLevel` в том же запросе, что и запись, а ядро само сравнивает его с уровнем, который требует операция (двухшаговая схема «спросили план, проверили, применили» поддавалась гонке; значение `maxLevel` вне `R1`/`R2` — отказ, без параметра только R1; main сверяет ещё и версию протокола ядра, со старым ядром запись отключена), а повышение подтверждается диалогом ОС (с 1.1.0 отдельным окном main; проверки окна отвечают в нём через QA-хук, которого нет в упакованной сборке); до 1.1.0 проверки окна подменяли `dialog.showMessageBox` в main и проверяют и согласие, и отказ (обход `APP_QA` убран: на этом пути аудит M3 нашёл дыру). **Аудит `checker` по M4 и что с ним сделано.** Нашёл девять дефектов, воспроизведённых на копиях. Исправлены, каждый с тестом:
1. **Профиль DeepSeek молча применял одну запись из двух.** Указатель (а с ним и id) содержал номер записи в списке `insert`; после выноса первой вторая «съезжала», получала другой id, и `apply_batch` её пропускал, сообщая об успехе. Теперь в указателе `id` записи из файла, а `apply_batch` пропускает только записи, которых не было и в предпросмотре, или уже готовые; пропавшая посреди пакета запись — остановка с ошибкой.
2. **Повышение R1→R2 гонкой.** main спрашивал уровень отдельным `plan`, а применял вторым вызовом; между ними страница могла вклинить `profileSave`. Теперь main передаёт ядру `maxLevel` в том же запросе, что и запись (`apply`, `rollback`, `rollbackBatch`, `applyProfile`), и ядро отказывает, если операции нужен уровень выше; без параметра ядро разрешает только R1. Откат операции R2 тоже требует R2.

4. **Путь домашнего каталога в плане и журнале** (введённая команда `<home>/bin/tool.exe`, скопированные аргументы): теперь заменяется на `~` той же функцией, что в скане.

6. **Устаревшая запись корзины блокировала вынос** (запись добавили заново руками, id тот же): теперь она перезаписывается, прежняя копия хранится в манифесте.

**Повторный аудит `checker` (по коммиту 7f0841a) и что с ним сделано.** Нашёл девять замечаний. Исправлены: (1) **со старым ядром проверка уровня не работала** (оно не знает `maxLevel`): main теперь сверяет версию протокола и со старым ядром отключает запись, а `pack`, `dist` и `e2e` сами пересобирают ядро; (2) **перезапись «устаревшей» записи корзины теряла данные**: теперь перезаписывается только такой же текст, а другой — отказ; (3) DeepSeek возвращал запись **по старым номерам** операции и записи в чужую операцию: при выносе сохраняется опора (`id` соседней записи), при возврате она проверяется, иначе отказ; (4) `rollback_batch` при R1 откатывал пакет наполовину: уровни всех операций проверяются до первого отката; (5) откат выноса искал запись **по имени** и мог вернуть чужую: для записей из корзины ищется только по id; (6) записи DeepSeek без простого уникального `id` (или с `/` и пробелом) больше не получают цели записи (остаются позиционными и не переключаются), указатель экранируется; (7) неверный `maxLevel` (`R0`, `r2`, число) — отказ, а не молчаливое R1; (8) комментарии и этот раздел приведены в соответствие с кодом; (9) `pack-check` закрывает только процессы со своим профилем и не принимает `PACK_DIR` со спецсимволами. Не исправлено сознательно (`shortcut:`): откат копии и правки в `~/.claude.json` идёт сверкой хеша и почти всегда откажет, пока Claude Code переписывает файл (откатывать нужно сразу, либо вынести запись в корзину); комментарий на отступе записи при выносе и возврате DeepSeek может оказаться после неё; возврат из корзины DeepSeek не проверяет совпадение `serverName` с записью, поставленной за это время. **Не проверялось:** форма удалённых MCP (`url` или `serverUrl`) у Antigravity и Claude Desktop по документации, поэтому копирование таких записей может дать нерабочую запись у получателя. Сухой прогон на настоящей машине: в нём `~/.claude.json` не сравнивается побайтово (файл самой сессии переписывается постоянно, прежнее сравнение проходило по везению), для него проверяется отсутствие временных файлов записи.

Тот же конвейер §5: предпросмотр (имена env, без значений), хеш-блокировка, бэкап, журнал, откат. Ядро проверяет имя (`[A-Za-z0-9._-]`, до 64), ровно один из `command`/`url`, форму env и отказывает, если у клиента уже есть запись с таким именем. Удалённый сервер (`url`) добавляется только в Claude Code (`type: http`) и Codex: форма у Desktop и Antigravity не сверена (адрес у Antigravity может лежать в `serverUrl`), там доступен только локальный. Адрес без хоста отвергается. Добавление не входит в пакеты и профили (у него нет записи, по которой пакет сверяет шаги). Две проверки ядра (`write.rs`: добавление в TOML и JSON, отказы) и сценарий e2e; независимая проверка `checker` нашла четыре мелких дефекта (адрес без хоста, указатель с точкой в TOML, пакет с добавлением, эхо введённого ключа env в ошибке), все исправлены. **Установки пакетов нет:** окно записывает строку запуска, `npx`/`uvx` скачает пакет при первом запуске клиента. Имя с точкой для Codex сверено на живом `codex 0.159.3` (изолированный `CODEX_HOME`): `codex mcp add my.server` пишет `[mcp_servers."my.server"]`, как и мы, и показывает запись в `mcp list`. (Codex при этом заменяет точку на `_` в имени инструмента для модели, так что `a.b` и `a_b` у одного клиента могут столкнуться: это его свойство, не наш отказ.)

**Установка плагина Claude Code** (кнопка «Установить плагин», R2), по документации Claude Code (plugin-marketplaces, marketplace-reference, CLI 2.1.325): маркетплейс → каталог → плагин.
- *Добавление маркетплейса*: `claude plugin marketplace add --scope user <источник>`. Источник проверяется в main (`app/src/main/install.ts`): GitHub `owner/repo`, адрес `https://` без логина и пароля или полный путь с буквой диска к папке с `.claude-plugin/marketplace.json` (или к самому `.json`). Пробелы в пути допустимы. Ведущий `-`, управляющие символы, `..`, сетевые `\\сервер\…`, `http:`, `file:`, `ext::`, `git@` отвергаются. Claude Code сам скачивает маркетплейс и пишет `~/.claude/settings.json` и `known_marketplaces.json`, это сказано в диалоге. Убрать — `claude plugin marketplace remove <имя>`.
- *Каталог* только читается: `known_marketplaces.json` → `installLocation` → `.claude-plugin/marketplace.json`. Имена, которые Claude Code не установит (не `^[A-Za-z0-9][A-Za-z0-9._-]*`), пропускаются. Описания очищаются от управляющих знаков и обрезаются до 300 символов. Отметка «установлен» берётся из `installed_plugins.json`. Плагин с источником `command` помечен как неустанавливаемый отсюда.
- *Установка* — выбор из списка, затем `claude plugin install <имя@маркетплейс> --scope user`. Всё идёт без оболочки (`execFile`), `-y` и `--accept-command` не передаются.

У добавления и установки общий порядок: предпросмотр с точной командой, отдельное подтверждение на R2. Один предпросмотр даёт один запуск той же команды. Это сеть и чужой код, и всё это вне конвейера §5: файлы правит сам Claude Code, в журнал Loadout запись не попадает, отката нет (снять плагин — выключить в матрице или `claude plugin uninstall`). e2e проверяет вызовы подставным `claude` на локальном маркетплейсе из `fixtures/marketplace`, настоящий CLI с сетью не запускался.

**Установка скила Claude Code** (кнопка «Установить скил», R2) идёт через конвейер §5 и попадает в журнал с откатом. По документации skills: личные скилы лежат в `~/.claude/skills/<имя>/SKILL.md` и подхватываются без перезапуска. Имена `synced` и `anthropic-skills*` заняты.
1. *Что и куда.* Окно показывает точную команду: для GitHub (`owner/repo[/путь]` или `https://github.com/owner/repo[/tree/<ветка>/<путь>]`) это `git clone --depth 1 --no-recurse-submodules [--branch <ветка>] -- https://github.com/owner/repo.git <бэкапы>/staging/…`, для папки — копия. Сети до следующей кнопки нет.
2. *Скачать или скопировать.* main собирает адрес из проверенных частей. git запускается с `protocol.ext.allow=never`, `core.symlinks=false`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`. Результат кладётся в каталог подготовки `<бэкапы>/staging/<32 hex>`. В нём ищутся каталоги со `SKILL.md`: корень или до трёх уровней.
3. *План ядра.* Намерение `installSkill {stage, sub, name}` не содержит путей: ядро само разворачивает номер подготовки и проверяет имя и путь внутри. В дереве не должно быть ссылок, `.git` пропускается, лимит — 1000 файлов и 50 МБ. Существующий скил не перезаписывается. В плане видны цель, число файлов, размер, список файлов и предупреждение о файлах кода. `base_sha` — хеш дерева.
4. *Применение.* Копия дерева уходит в каталог операции. Затем дерево копируется во временный `~/.claude/.<имя>.loadout.tmp` (тот же том, не внутри `skills/`), переносится `rename`, и хеш сверяется.
5. *Откат.* Он возможен, пока хеш дерева совпадает с установленным. Цель пересчитывается из имени, а не из пути в манифесте. Каталог сначала копируется в бэкап операции отката, потом убирается.

e2e клонирует локальный git-репозиторий из `fixtures/skill-src` (адрес GitHub подменяет `LOADOUT_GITHUB_BASE`, только в разработке) и проходит путь установка → матрица → откат.

Скачивание требует R2 уже в main. Папка больше 1000 файлов или 50 МБ отвергается до копирования. Файлом кода считается всё, что не `.md/.txt/.json/.yaml/.csv`, в том числе файл без расширения. Отдельное предупреждение получает `SKILL.md` с `` !`команда` `` или `allowed-tools`. Откат сначала убирает каталог (`rename`, на другом томе — удаление с возвратом из копии при сбое) и только потом пишет строку журнала. Если `~/.claude/skills` — ссылка на другой том, установка копирует на место без `rename`.

Ветка в адресе `tree/…` и `blob/…` может содержать `/`: перед загрузкой `git ls-remote --heads --tags` даёт имена, берётся самое длинное начало сегментов, совпавшее с веткой или тегом (ветки `a` и `a/b` в git не уживаются); не ответил список или нет совпадения — остаётся «первый сегмент — ветка», и при ошибке клона текст подсказывает указать адрес без `tree/…`. Хеш коммита (7–40 hex) в `tree/<sha>/…`: `--branch` его не принимает, поэтому клон без выгрузки (`--no-checkout --filter=blob:none`, без `--depth`) и `git checkout --detach <sha> --` вторым шагом (проверено на локальном репозитории с коротким хешем). Для маркетплейса `claude plugin marketplace add` принимает `owner/repo[#ветка|тег]`, полный адрес клона (`https://…`, `git@host:path`; `ssh://` разбирается так же строго, но в документации прямо не назван) и путь (документация Claude Code, «Add a marketplace»; `claude plugin marketplace add --help` форматов не перечисляет); хеш коммита после `#` документация не называет («pin a branch or tag»), он отклоняется с пояснением. SSH-адрес проверяется по частям (пользователь, хост, путь: ни пробелов, кавычек, управляющих знаков, `..`, `%`, `-` в начале), `ssh://` разбирается вручную, а не `new URL`, который сворачивает `..`. Журнал кеширует хеши файлов скила по (путь, mtime, размер), повторный показ файлы не читает. Обновления скила нет, сначала откат или удаление. Установка в проект (`.claude/skills` проекта) не сделана. Другие клиенты: у Codex, Antigravity и Desktop нет документированного CLI установки плагинов, в приложение не включены. `shortcut:` откат добавления в `~/.claude.json` идёт сверкой хеша и обычно откажет, пока Claude Code переписывает файл; обратная операция (удаление записи) не сделана.

**Плагины и MCP в матрице разведены** по разным группам и строкам (`aggregate.ts`): раньше один логический ключ сводил плагин и одноимённый MCP в одну строку.

**Два языка интерфейса (RU/EN).** Строка пишется парой на месте появления: `t('русский', 'english')` в окне и main (`app/src/shared/i18n.ts`), макрос `tr!("русский", "english")` в ядре (`crates/loadout-core/src/i18n.rs`). Язык ядра — один на процесс (`loadout serve --lang ru|en`, по умолчанию `ru`), в тестах не переключается; смена языка в окне перезапускает ядро с новым `--lang` и пересоздаёт дерево окна. Язык по умолчанию — по локали системы (`ru*` — русский, иначе английский), выбор хранится в `settings.json` рядом с уровнем записи; `LOADOUT_LANG` — только для разработки и e2e. Ветвление по русскому тексту убрано (название кнопки корзины выбирает структурное поле `Plan.trash`). Подписи на уровне модуля вычисляются функциями, а не при импорте. Язык хуков Инструментов контекста (`context-toolkit setup --lang`) — отдельная настройка установленных хуков; в форме он по умолчанию равен языку окна и задаёт также язык всего вывода `setup` и `setup --uninstall` (единый `msg!(en, ru)` в ядре Инструментов контекста, разметка `[dry-run]`, `[warn]`, `[note]`, `ERR:`, ` -> `, флаги, пути и имена не переводятся), поэтому в русском окне `pre.out` по-русски, а в английском без кириллицы; `context-toolkit doctor` получает язык окна. e2e гоняет русские сценарии с `LOADOUT_LANG=ru`, а затем английский проход: все разделы, диалоги, план и ошибка ядра, ни одной кириллической буквы в тексте и атрибутах, переключатель туда и обратно. Журнал: тексты `from`/`to` хранятся в манифесте на языке операции, но при показе стандартные слова и префиксы («включено», «в корзине Loadout», «нет записи», «копия: », «добавить: ») переводятся на текущий язык (`relang` в `write.rs`); команда, введённая пользователем, не переводится. Смена языка отказывает, пока идёт запись или установка (она останавливает ядро), и сбрасывает сверку версии протокола нового процесса. Сетка хуков прокручивается по горизонтали (событий бывает больше, чем помещается). **Пределы:** очередь запросов ядра одна, поэтому залп запросов, пришедший раньше события файла, законно обрабатывается раньше него (`MAX_WAIT` ограничивает отсрочку скана при непрерывном потоке, а не при залпе); тест `request_flood_…` теперь подаёт тяжёлые запросы не залпом, а равномерно. Не проверялись: первый запуск упакованной сборки на английской локали системы, текст системного диалога повышения уровня на английском, удаление через деинсталлятор.

Цена: отрисовка программная; в этих замерах разницы по процессору между полными и выключенными эффектами не видно (47 и 188 мс, шум от живых конфигов).

### 10.8 Встроенные Инструменты контекста (установка, применение, эффективность)

**Устройство.** Бинарь Инструментов контекста собирается из крейта `crates/context-toolkit` этого же воркспейса и кладётся в `app/build/context-toolkit.exe` (`npm run bundle:context-toolkit`, его же зовут `pack` и `dist`; источник — `CONTEXT_TOOLKIT_BIN` (старое имя `CTXKIT_BIN` принимается) или `target/release/context-toolkit.exe`), оттуда `electron-builder` берёт его в `resources/context-toolkit.exe`. main запускает **только этот** бинарь по зашитому пути (`execFile`, без оболочки, таймауты 20–120 с); чужие копии (`~/.claude/hooks/context-toolkit.exe`, `~/.local/bin/context-toolkit.exe`) не запускаются, а только сравниваются побайтово со встроенным (совпадает, отличается, нет). Раздел «Инструменты контекста» (клавиша 7). При прежней установке раздел показывает строку «Установлена прежняя версия (ctxkit): нажмите «Применить», чтобы перейти на «Инструменты контекста»»; применение переводит её на новое имя (см. §13).

**Установка и применение.** `context-toolkit setup` сам копирует текущий бинарь в `~/.claude/hooks` (путь из хуков) и `~/.local/bin` и прописывает хуки и настройки, поэтому «установить» и «обновить» — одна и та же команда, а путь хуков остаётся стабильным, даже если приложение переустановят. Форма: Claude Code всегда; флажки «блок правил в CLAUDE.md», Claude Desktop, Antigravity, DeepSeek Harness; язык и три селекта со значением «Не менять (по умолчанию)»: основная модель (`--main-model sonnet|opus|haiku`), effort (`--effort low|medium|high|xhigh`) и модель-советник (`--advisor`). Флаг передаётся только при явном выборе: значение по умолчанию не выбор пользователя, `context-toolkit setup` без флага не трогает ни `model`, ни effort, ни `advisorModel`; прежнее и новое значение видны в предпросмотре строками Инструментов контекста «было -> стало». Под селектами подсказки: effort пишется для основной модели (`modelSettings.<модель>.effortLevel`, нужен Claude Code 2.1.251 или новее, и верхний `effortLevel`). Страница передаёт только булевы значения и перечисления (`parseSetupOptions`), ни одного пути или произвольной строки в аргументы не попадает. **Предпросмотр** (`setup --dry-run`) ничего не пишет и доступен на любом уровне; **применение** требует R2 и предпросмотра с точно такими же настройками (проверяет main, а не страница: без него отказ даже при прямом вызове IPC). Вывод Инструментов контекста показывается как текст, путь домашнего каталога заменён на `~`. Свои бэкапы Инструменты контекста делают сами (`~/.claude/backups`). Если запущен Claude Desktop, Инструменты контекста при флажке Desktop пропускают запись и сами предупреждают.

**Откат.** Кнопка «Откатить Инструменты контекста» показывает предпросмотр (`setup --uninstall --dry-run`), затем «Откатить: убрать хуки, блок правил и бинарь» выполняет откат; как у применения, нужны R2 и свежий предпросмотр, который проверяет main (отдельный IPC `ctxkit:uninstall`; один ключ предпросмотра с видом действия, поэтому предпросмотр применения не разрешает откат и наоборот; общий замок «Инструменты контекста уже работают»). Аргументы строит `uninstallArgs` только из двух булевых флагов (Antigravity, DeepSeek Harness) и языка интерфейса; флаги самого `setup` (`--with-rules`, `--advisor` и др.) с `--uninstall` Инструменты контекста отвергают, поэтому они не передаются. Пресеты Claude Desktop откат не трогает, флаг `--desktop` ему не нужен. Откат убирает только поставленное `setup`: хуки (и шлюз Stop), блок правил, бинарь хуков; модель, советник, effort, пресеты и агентов Explore и checker оставляет, а в выводе Инструменты контекста печатают список «не тронуто» с текущими значениями и путём к бэкапу `settings.json`. В разработке и проверках пути Antigravity и DSH передаются только вместе с галочкой (Инструменты контекста включают их сами по флагам путей). Форма: занятая кнопка показывает «Считаю…» (или «Применяю…», «Откатываю…») со спиннером, строка состояния под кнопками говорит, что идёт, остальные кнопки заблокированы.

**Диагностика и эффективность.** `doctor --json` показывается списком находок (ok, к сведению, внимание, ошибка, со словом, не только цветом) с подсказкой исправления. `report --json --days 7|14|30` даёт счётчики из транскриптов Claude Code: ходы основной сессии по моделям (доля Sonnet/Haiku и Opus/Fable), ходы субагентов, вызовы советника и агентов, объём результатов инструментов (в том числе чтений файлов и осмотра оболочкой), число остановленных чтений, вызовы и объём `context-toolkit check`; по дням со столбиком моделей. Ответы разбираются по форме (`schema: 1`, `tool: ctxkit`), чужая версия контракта отвергается, ключи агентов (их пишет модель) режутся по виду. **Честная оговорка в самом окне и здесь:** у отчёта нет базовой линии «до Инструментов контекста», поэтому «сэкономлено» не считается; эффект виден как динамика долей и остановленных чтений по дням после применения.

**Проверки.** vitest (разбор и аргументы, доли и сегменты, 8 тестов); e2e на копии фикстуры с подставными транскриптами: версия, статус «нет», применение недоступно без предпросмотра, отказ main при прямом вызове (без предпросмотра, неверный язык, при R0), предпросмотр ничего не меняет (хеш `settings.json`), смена настроек гасит предпросмотр, применение ставит бинарь, пишет хуки и делает бэкап, статус становится «совпадает», диагностика и таблица по дням, axe, нет горизонтальной прокрутки. Позже добавлены: селекты основной модели и effort (по умолчанию в `settings.json` ничего не появляется; Sonnet + high даёт строки в предпросмотре и после применения `model` и `modelSettings.claude-sonnet-5-5.effortLevel`), откат на копии фикстуры (отказ main без предпросмотра отката и при R0, предпросмотр ничего не меняет, чужие хуки на месте, в `settings.json` нет записей Инструментов контекста, модель и советник оставлены, повторный откат безопасен), замер выравнивания формы на 1100, 1280 и 1920 (`getBoundingClientRect`), состояние занятости кнопки. В разработке и проверках (`LOADOUT_HOME`) Инструменты контекста работают в этом каталоге (`--profile`, `--desktop-file`, `--agy-file`, `--dsh-home`), настоящий профиль не трогается; на упакованной сборке по настоящему профилю проверены только чтение (версия, 6 находок, отчёт за 14 дней), `setup` по настоящему профилю не запускался. Снимки `state/m5-ctxkit-*.png`.

**Аудит `checker` по встраиванию (последний круг).** Потери данных и записи в настоящий профиль не нашёл (по коду `setup.rs`: все места записи уходят по переданным путям, при `--profile` копия в `~/.local/bin` отключается, `--dry-run`, `doctor` и `report` ничего не пишут). Исправлено: (1) запись можно было отправить перезапущенному ядру без сверки версии (запрос ждал в очереди на время перезапуска) — теперь сверенное «поколение» процесса привязано к запросу записи, перезапущенному ядру он не уходит; (2) `ctxkit:setup`: один предпросмотр расходуется до запуска, параллельный второй запуск отвергается, при применении передаётся `--skip-version-check` (Инструменты контекста проверяют версию `claude` уже после записи, и зависший `claude` оставил бы окно с ошибкой при изменённых файлах); (3) находки `doctor` проходят замену пути дома на `~`; (4) подложка диалогов не тянет окно как заголовок; `e2e` проверяет наличие встроенного бинаря. Кроме того, после вопроса о том, не касался ли e2e настоящего профиля: метки времени подтвердили, что нет, а в изоляцию добавлен `--claude-json` (Инструменты контекста читали `~/.claude.json` для диагностики) и e2e теперь сверяет хеши настоящих файлов, которые пишет `setup`, и число настоящих бэкапов до и после. **Не исправлено:** корзина может содержать скрытую копию, которую окно не показывает, пока запись жива в файле (данные целы в `backups/trash/<id>.json`, выхода через окно нет); записи DeepSeek, вынесенные сборкой до исправлений аудита, без опоры в корзине не вернуть; опора возвращается только в обратном порядке выноса; `rollback_batch` проверяет уровень и у уже откатанных участников и при сбое посреди пакета теряет список сделанных откатов; один неверный день в отчёте роняет весь отчёт, огромные суммы дают «Infinity»; сообщение про `~/.claude/backups` верно только для Claude Code (у остальных клиентов копии рядом с файлами); `bundle-context-toolkit` берёт рабочее дерево соседнего репозитория вместе с незакоммиченными правками; `CLAUDE_CONFIG_DIR` и `DSH_HOME` из окружения Инструменты контекста учитывают, а статус копий считается по профилю по умолчанию; не покрыты тестами `run()` и `status()`.

**Не сделано.** Возврат модели, советника и effort к прежним значениям при откате (Инструменты контекста их прежних значений не знают: печатают текущие и путь к бэкапу, вернуть можно вручную или из бэкапа); откат пресетов Claude Desktop и агентов (Инструменты контекста их не трогают); «до и после» как отдельная метка начала работы Инструментов контекста (в отчёте её нет); выбор профиля Claude Code (`--profile`, `CLAUDE_CONFIG_DIR`): окно работает с профилем по умолчанию. Версия Инструментов контекста в приложении — та, что собрана из репозитория в момент упаковки: рассинхрон с установленным у пользователя показывает статус «другая версия».

**Шлюз Stop (добавлен позже, `crates/context-toolkit/src/gate.rs`).** `context-toolkit setup` по умолчанию добавляет хук `Stop`: если за ход правились два и более файла с кодом (или пять и более правок), а после последней правки не вызван ни `checker`, ни advisor, остановку блокируют один раз (повтор пропускает `stop_hook_active`). Хук читает только хвост транскрипта (4 МБ), команд не запускает, при любой ошибке молчит; в `doctor` для него находка `stop_gate`; флаг `context-toolkit setup --no-stop-gate` его убирает, `CONTEXT_TOOLKIT_GATE=0` глушит на сессию. Причина: одних правил в `CLAUDE.md` Sonnet не выполняет (до 14.11 вызовов advisor в отчёте 0). Применён к профилю владельца (бэкапы `settings.json` и `CLAUDE.md` в `~/.claude/backups`). Проверено: тесты крейта, clippy, `guard.test.mjs`, процессные прогоны на синтетическом и на обрезанной копии реального транскрипта (блок), независимый `checker` (24 краевых случая), юнит-тесты и e2e окна; замер ~50 мс на транскрипте 302 МБ вместе с запуском процесса. Живая проверка (15.11, `claude -p` 2.1.325 с haiku на временном профиле, `context-toolkit setup --profile`): правка двух файлов, Stop блокирует один раз, на повторе (`stop_hook_active`) хук молчит и ход завершается. Принятые ограничения (слепые зоны): (1) правки, сделанные субагентами, и правки через Bash не видны: транскрипты субагентов лежат в отдельных файлах `<сессия>/subagents/agent-*.jsonl`, в основном виден только вызов `Agent`; учитывать их значило бы сопоставлять файлы с ходом по времени, это не дёшево и даёт ложные блокировки; (2) если первым остановку блокирует чужой `Stop`-хук, на повторе приходит `stop_hook_active=true` и наш промолчит: платформа не говорит, чей именно блок, а надёжно отличить его можно только состоянием на диске; (3) пути с `/temp/` и `/tmp/` считаются черновиками и не учитываются, поэтому проект во временном каталоге шлюз не сработает (так живую проверку пришлось вести вне `Temp`). Что осталось (сравнение вызовов advisor и `checker` по дням) — в `TODO.md` в корне репозитория.

**Политики (добавлены позже, `crates/context-toolkit`, `context-toolkit.json`).** Защиты, которые владелец держал в `CLAUDE.md` текстом, стали хуками, а блок правил собирается из одного источника. Они **выключены, пока `context-toolkit setup --policy <список>` их не включит** (ничего не включается молча; без флага файл не создаётся и не меняется), выбор лежит в `<профиль>/context-toolkit.json`: `commit_hygiene` (`git commit` с `Co-Authored-By` / `Generated with` в сообщении запрещается), `confirm_irreversible` (`ask` для `git push` и `push --delete`, `reset --hard`, `clean -f`, `branch -D`, `checkout .` / `restore .`, `stash drop` / `clear`, `reflog expire --expire=now`, `gc --prune=now`, `prune`, `worktree remove --force`, `update-ref -d`, `rm -rf`, `find -delete`, `Remove-Item -Recurse -Force` под любым алиасом, `rd /s /q` / `del /s /q` внутри `cmd /c`, корня диска и домашнего каталога; видит команду и за обёртками `sudo`, `env`, `timeout`, `xargs`, `bash -lc`, `pwsh -c`, `cmd /c`), `stray_files` (`ask` для `Write` файлов `report*.md`, `notes*.md`, `*.tmp`, `*.bak` и подобных в корне проекта или профиля), `build_slots=N` (`context-toolkit check` берёт один из N слотов на временную папку). `--with-rules` добавляет в блок по строке на каждую включённую политику и свои пункты владельца `rules`; `doctor` находит повторяющиеся правила в `CLAUDE.md` (`rules_duplicate`: одинаковую формулировку между любыми строками и пересказ строки блока Инструментов контекста своими словами — по общим якорям в `коде`/**жирном**, именам моделей и группам синонимов-глаголов на двух языках; без модели и сети; на корпусе тестов 18 из 18 пересказов и 0 ложных пар, на слепом наборе, под который ничего не подгоняли, 7 из 10 и 0 ложных; исключение из правила блока повтором не считается). Хук, который не смог прочитать файл или команду, молчит, а командные политики разбирают строку оболочки (кавычки, `$(...)`, heredoc, here-string PowerShell), чтобы те же слова в сообщении коммита их не вызывали. Откат: `--policy none` или `--uninstall` (файл удаляется, только если его создал `setup` и владельческого в нём нет). Что делает `ask` хука при `bypassPermissions` и `dontAsk`, документация не говорит; вживую на `claude` 2.1.325 (2026-11-16) он сработал во всех режимах, где до него дошёл вызов, включая `bypassPermissions` и `--dangerously-skip-permissions`: в `-p` вызов отклоняется с нашей причиной, а хост сессии stream-json получает запрос `can_use_tool` с этой причиной и вызов выполняется только после «allow»; диалог в терминальном интерфейсе и режим `auto` не смотрели, поэтому то, что не должно случиться никогда, держи в `deny`. Таблица «как включить, выключить, чем проверено» — в `crates/context-toolkit/README.ru.md`. **В окне** (раздел «Инструменты контекста», блок «Защиты»): селект «Политики» — «Не менять (по умолчанию)» (флаг `--policy` не передаётся, `context-toolkit.json` не создаётся), «Включить выбранные» (четыре чекбокса: гигиена коммитов, подтверждение необратимого, неожиданные файлы-отчёты, лимит параллельных сборок с числом 1–8) или «Выключить все» (`--policy none`); `parseSetupOptions` принимает только перечисление режима, булевы значения и целое 1–8, аргумент `--policy commit-hygiene,confirm-irreversible,stray-files,build-slots=N` собирается из закрытого списка. Находка `policies` из `doctor` даёт только подпись «Сейчас включены: …», в форму и в аргументы ничего не попадает. Предпросмотр показывает строки «политика …: выкл -> вкл», откат убирает `context-toolkit.json`, если его создал `setup` (e2e: «не менять» файла не создаёт, «включить выбранные» с двумя политиками создаёт, откат из окна убирает).

### 10.10 Автообновление из релизов GitHub (добавлено позже, к 1.0.0)

**Устройство.** `electron-updater` с провайдером GitHub (`publish` в `package.json`): `npm run dist` кладёт рядом с `Loadout.Setup.X.Y.Z.exe` и `.blockmap` файл `latest.yml`, а в сборку — `resources/app-update.yml`. Имя установщика задано (`nsis.artifactName`) таким же, как у релизов, без пробелов: иначе `latest.yml` ссылался бы на имя, которого в релизе нет. `--publish never` в `pack` и `dist`: сборка ничего не выкладывает сама. Логика без electron вынесена в `app/src/main/updates.ts` (юнит-тесты `updates.test.ts`): `autoDownload = false`; новая версия — только строгое `X.Y.Z` больше текущей (пре-релизы и мусор из ленты не предлагаются); расписание — первая проверка через 10 с после запуска, дальше раз в сутки по настенным часам с тиком раз в час (суточный таймер уплывал бы через сон и гибернацию); неудачная проверка повторяется на следующем часовом тике, а не через сутки; найденную, но не скачанную версию фон не перепроверяет (предложение не пропадает из-за сбоя сети); пока идёт скачивание или обновление готово, проверки не перебивают состояние; включение галочки сразу запускает проверку. Ошибка уходит в окно только причиной (`offline`, `missing`, `corrupt`, `check`, `download`, `install`), фразу на текущем языке подставляет окно, сырой текст со стеком и адресами остаётся в main; ошибка фоновой проверки «тихая» (видна только в панели), ручной проверки, скачивания и запуска установки — карточкой. Окно получает только проверенную версию, проценты и причину ошибки; заметки релиза (HTML из ленты) не передаются, ссылку «Что нового» строит main из версии и открывает `shell.openExternal`. IPC: `updates:get`, `updates:setAuto` (только boolean), `updates:check`, `updates:download`, `updates:install` (отказ, пока идёт запись или установка — как у смены языка), `updates:notes`; все через `assertTrusted`. Настройка `autoUpdate` в `settings.json`, по умолчанию включена (выключена только явным `false`). Установка: `quitAndInstall(true, true)` — тихо в ту же папку и запуск новой версии; если не нажать, обновление ставится при выходе (`autoInstallOnAppQuit` по умолчанию).

**Окно.** В правом конце нижней строки — кнопка с версией (зелёная с точкой, когда есть что ставить) открывает панель: установленная версия, галочка «Проверять обновления автоматически», «Проверить сейчас», состояние и строка о приватности. Карточка над нижней строкой справа: «Доступна версия X» со «Скачать» и «Что нового (GitHub)», затем «Скачивается версия X: N%» с полосой, затем «Версия X скачана и проверена» с «Перезапустить и обновить»; после неудачной ручной проверки — спокойная фраза и «Повторить». Карточка не модальная, скрывается крестиком. Подпись в нижней строке честная: при включённой автопроверке «сам Loadout ходит в сеть только за обновлениями (GitHub)», при выключенной — «сам Loadout в сеть ничего не отправляет». При первом запуске карточка приветствия над разделом говорит то же: сам Loadout выходит в сеть только за проверкой обновлений, и выключается она этой кнопкой; закрытие карточки запоминается в `settings.json` (`welcomed`). Сообщения о действиях всплывают слева над нижней строкой и с этой карточкой не пересекаются (e2e меряет это на 1100, 1280 и 1920).

**Приватность.** Запросы идут только на `github.com` (`releases.atom`, `releases/latest`, `latest.yml`) и на файловый сервер GitHub (`release-assets.githubusercontent.com`), `api.github.com` провайдер для github.com не использует. User-Agent у electron-updater общий, `electron-builder`. Найденное по ходу: библиотека шлёт в заголовке `x-user-staging-id` случайный идентификатор из `<профиль>/.updaterId` (для поэтапной раздачи) — постоянный на установку, то есть по нему можно было бы связать проверки одной машины; Loadout подменяет его постоянными нулями (`requestHeaders`). Проверено по журналу локального сервера: заголовки `user-agent: electron-builder`, `x-user-staging-id: 00000000-…`, `accept-language` (язык системы), больше ничего.

**Неподписанный установщик.** Подпись скачанного обновления electron-updater проверяет только при `publisherName` в `app-update.yml`; без сертификата его там нет, шаг пропускается (иначе каждое обновление отклонялось бы как «not signed by the application owner»). Защита — SHA-512 из `latest.yml`, полученного по HTTPS из релиза: несовпадение после полного скачивания — отказ, после дифференциального — откат на полное скачивание и та же проверка. Веб-установщик выключен (`disableWebInstaller`). `pack-check` проверяет, что `app-update.yml` указывает на `d-ridelman/Loadout` и не содержит `publisherName`, а после `dist` — что `latest.yml` совпадает с установщиком по имени и SHA-512 и рядом есть `.blockmap`. Что не защищено: кто может выпустить релиз в репозитории, может выпустить любой код (как и при ручной загрузке).

**Проверки.** e2e: в режиме QA main не трогает `autoUpdater`, а ставит заглушку-эмиттер (`globalThis.__loadoutUpdater`), которую сценарий ведёт через `app.evaluate`: галочка по умолчанию включена; «Проверить сейчас» → «Проверяем…» → ошибка сети без сырого текста; «Доступна» (HTML заметок не попадает в окно, ничего не скачивается само), «Что нового» открывает ровно страницу релиза, «Скачать» → 42 % → «Перезапустить и обновить» → `install:true:true`; axe по карточке и панели; галочка выключается, сохраняется в `settings.json` и переживает перезапуск; снимки 1280 и 1920. `pack-check` запускает сборку с `autoUpdate: false` в профиле (проверка не ходит на GitHub) и видит «Ещё не проверялось». **Настоящее обновление проверено локально** (17.11.2026): две сборки 0.9.0 и 0.9.1 из одного кода с переопределённым конфигом electron-builder (`extraMetadata.version` и `name`, другие `appId`, `productName`, `shortcutName`, без ярлыков, `publish: generic` на `http://127.0.0.1`), раздача `latest.yml`, exe и обоих `.blockmap` локальным сервером с поддержкой Range; 0.9.0 тихо поставлена в `/D=` во временный каталог. Автопроверка нашла 0.9.1 через ~10 с после запуска без нажатий, «Скачать» скачало дифференциально (один запрос с 7 диапазонами вместо 124 МБ), «Перезапустить и обновить» за ~15 с заменило установку на 0.9.1 в том же каталоге и запустило её с `--updated`; затем тестовая копия удалена деинсталлятором, её профиль и кэш стёрты. Установка владельца (`%LOCALAPPDATA%\Programs\Loadout`), его данные (`%APPDATA%\loadout-app`), ключи удаления и ярлыки сверены до и после — не изменились. Не проверено: настоящий GitHub (релиза с `latest.yml` ещё нет), обновление установки «для всех пользователей», работа через прокси. **Позже проверено на настоящем GitHub** (17.11.2026, выпуск 1.1.0): установленная у владельца 1.0.0 сама нашла 1.1.0, скачала и проверила её, «Перезапустить и обновить» поставило 1.1.0; отдельно — тот же путь с закрытием окна вместо кнопки: установка при выходе за ~16 с, программа после неё не запускается.

### 10.11 «Похожие скилы» (ML, после 1.1.0)

**Устройство.** В инспекторе у скила — до трёх скилов с близким по смыслу описанием (другие логические ключи; из копий одного скила с одинаковым текстом показывается копия в клиенте выбранной ячейки). Текст — `имя: описание` в том виде, как его показывает ядро (маска, 200 символов). Векторы считает отдельная программа `loadout-ml.exe` (крейт `crates/loadout-ml`): `paraphrase-multilingual-MiniLM-L12-v2` int8 через ONNX Runtime 1.31.0, статически влинкованный (сборка pyke.io, `ort` сверяет её sha256 при компиляции), mean pooling, нормировка, 128 токенов, **по одному тексту**: модель квантует активации на весь тензор, поэтому дополнение в пачке меняло бы вектор текста (проба `ml-eval/results/runtime_probe.json` в локальном репозитории замеров). main запускает её только при поиске похожих, держит векторы в памяти на время работы окна, одну задачу за раз (устаревший запрос пропускается), с таймаутом 120 с; ранжирование (`app/src/main/similar.ts`, `nearest`) от источника векторов не зависит, и e2e идёт на поддельной программе `app/e2e/fake-ml.mjs`.

**Сеть и данные.** Модель (два файла закреплённой ревизии, 118 453 870 + 9 081 518 байт) скачивается только по кнопке «Скачать модель» с `huggingface.co` (редирект на `us.aws.cdn.hf.co`) в `%APPDATA%\loadout-app\models\`; каждый файл сначала пишется в `.part` и получает имя только при совпадении размера и sha256; скачивание без данных 60 с прерывается; перед первым использованием в каждом запуске sha256 проверяется снова, при несовпадении окно предлагает скачать заново (перекачивается только испорченный файл). Описания скилов никуда не уходят. Подмена адреса, файлов и программы для проверок — только в режиме QA.

**Зависимости.** Сборка ONNX Runtime от pyke.io собрана с DirectML, поэтому `loadout-ml.exe` импортирует системные DirectML, D3D12 и DXGI (есть в Windows 10 1903+ и Windows 11; модель всё равно считается на процессоре) и библиотеки Visual C++ (`msvcp140`, `msvcp140_1`, `vcruntime140_1`; `loadout.exe` и раньше требовал `vcruntime140`). Чтобы программы запускались без установленного VC++ Redistributable, установщик кладёт эти четыре DLL рядом с ними (`app/scripts/bundle-vcruntime.mjs`, распространяемые файлы Visual Studio); `pack-check` проверяет их наличие. Копию `context-toolkit.exe`, которую установка Инструментов контекста кладёт в `~/.claude/hooks`, это не покрывает: ей по-прежнему нужен `vcruntime140` в системе. На чистой Windows без Redistributable запуск не проверялся. Лицензии: `licenses/` (ONNX Runtime с его сторонними уведомлениями, список крейтов из `node tools/notices.mjs`).

**Цена.** Установщик: +`loadout-ml.exe` 26 МБ (замер: 115,2 → 121,2 МБ вместе с DLL рантайма). Первый поиск на 117 скилах владельца со скачиванием — 9 с, дальше ~0,3 с. `loadout-ml.exe` на время поиска (~4–5 с) занимает до 490 МБ: 268 из них — разбор словаря токенизатора (250 тыс. слов), остальное — ONNX Runtime; опции ONNX Runtime (арена, шаблон памяти, предупаковка, уровень оптимизации) пик не меняют. Своё сжатое представление токенизатора уменьшило бы память, но это был бы не тот файл, что проверен по sha256; оставлено.

**Качество (замеры в локальном репозитории `ml-eval` с данными владельца, в публичный репозиторий не входит; оценки — модели-судьи, не владелец).** Часть 2 (до исправления многострочных описаний, 19 строк): MiniLM полезнее триграмм (12/19 против 9/19), дубликаты — no-go (у MiniLM дубликатом оказался 1 кандидат из 13). Этап 3 (117 скилов владельца, исправленные описания, условия записаны до прогона, половина строк отложена для вердикта): у текущего варианта на отложенной половине близки 41 % подсказок, хотя бы одна полезная у 71 % скилов; смесь с триграммами (40 %) и полный текст описания вместо 200 символов (40 %) прироста не дали; порог по косинусу 0,53 поднимает точность до 55 %, но подсказки остаются у 58 % скилов при заранее заданном минимуме 60 % — не принят. Отклонение: судья Opus дважды остановлен фильтром безопасности на части описаний, оба судьи и третий для 16 споров — независимые прогоны Sonnet, поэтому их согласие (300/316) завышено одинаковыми предпочтениями одной модели. Поэтому в окне это «подсказка, не дубликат», и в Доктор оно не выводится.

## 11. Риски и открытые вопросы

- **Форматы неофициальные.** Любой апдейт клиента может их поменять. Смягчение: версия адаптера, `unknown` вместо падения, golden-тесты.
- **Клиент перезапишет наш файл.** Для этого проверка процесса и оптимистичная блокировка; полностью исключить гонку нельзя.
- **DeepSeek harness:** формат разобран (§2), но у записей `cordis.patch.yml` не видно флага «выключено»: есть только `reconnect.enabled`. Поэтому «выключить» для dsh, вероятно, означает убрать запись из файла. Loadout кладёт её копию в свою корзину и возвращает при включении. Схема `dsh-mcp-client` в M1 получена скачиванием публичного пакета (`npm pack` в изолированный каталог, ничего не запускалось): флага «выключено» у записи действительно нет (§10.2). Локально пакеты dsh в `~/.dsh/profiles/node_modules/@deepseek-ai` — junction'ы в `AppData\Local\npm-cache\_npx\…`, и цель junction'а `dsh-mcp-client` у владельца не существует (ссылка битая). Битая junction — готовое состояние `broken` для Доктора (пока не реализовано).
- **Файл `cordis.patch.yml` пишут многие.** Рядом лежат бэкапы от `glidehand`, `sparehand`, `netatlas`, `rea`, `orca`: установщики этих инструментов сами правят файл. Значит, гонка записей реальна, а оптимистичная блокировка по хешу (§5) обязательна, и формат YAML с тегом `!!js` нельзя перезаписывать целиком. Правка — только точечная по тексту.
- **ChatGPT desktop:** на машине это и есть приложение `OpenAI.Codex` (§2).
- **`antigravity/mcp/*/*.json`:** возможно кеш схем, а не конфиг. Не пишем в него никогда.
- **Копирование сущности между клиентами** (M4) требует трансляции форматов (например, MCP из JSON в TOML). Для хуков семантика событий различается, переносим только совпадающие события и честно показываем потери.

## 13. Интеграция с Инструментами контекста (`crates/context-toolkit`)

**Переименование (решение владельца).** Встроенный инструмент, раньше называвшийся ctxkit, теперь называется «Инструменты контекста»; команда и файлы — `context-toolkit` (`context-toolkit.exe`), крейт — `crates/context-toolkit`, файл политик — `<профиль>/context-toolkit.json`, переменные — `CONTEXT_TOOLKIT_GUARD`, `CONTEXT_TOOLKIT_GATE`, `CONTEXT_TOOLKIT_LANG` (старые `CTXKIT_*` поддерживаются, при обеих действует новая), маркеры блока правил — `<!-- context-toolkit:start -->` / `<!-- context-toolkit:end -->`. Старое имя распознаётся всегда, а `context-toolkit setup` переводит прежнюю установку: хуки с `ctxkit.exe` (и старые `claude-guard` / `no-inline-backslash`) переписываются на `hooks/context-toolkit.exe`, чужие не трогаются; старый `hooks/ctxkit.exe` удаляется только после успешной записи `settings.json` (остаётся, если его ещё используют хуки Antigravity или DSH, а setup запущен без `--antigravity` / `--dsh`; если Windows не даёт удалить, печатается «удалите вручную: <путь>», код выхода 0); `~/.local/bin/ctxkit.exe` удаляется, только если он наш и блок правил старого имени уже не велит запускать `ctxkit check`; `--with-rules` переводит старый блок на новые маркеры; `ctxkit.json` копируется в `context-toolkit.json` (старый, созданный setup, удаляется, когда старый бинарь больше не нужен, написанный владельцем остаётся); `env.CTXKIT_LANG` заменяется на `CONTEXT_TOOLKIT_LANG`; ключ Antigravity и блок DSH заменяются при `--antigravity` / `--dsh`. `--uninstall` убирает и новое, и старое. `doctor` выдаёт находку `legacy_name`, если что-то осталось на старом имени, а окно показывает «Установлена прежняя версия (ctxkit): нажмите «Применить», чтобы перейти на «Инструменты контекста»». Подробности — в `crates/context-toolkit/README.ru.md`, раздел «Переход с ctxkit». Ниже прежнее имя оставлено там, где оно историческое (имя репозитория, метки хуков в данных того времени, слова владельца).

**Репозитории объединены (решение владельца).** Основной проект — Loadout; Инструменты контекста (тогда ctxkit) теперь крейт `crates/context-toolkit` в том же Cargo-воркспейсе (история его коммитов сохранена слиянием поддерева, прежняя ветка `main` GitHub-репозитория `d-ridelman/ctxkit` — предок новой; репозиторий переименован в `d-ridelman/Loadout`; до публикации он был приватным). Общий `Cargo.lock` и `target/` в корне; профиль `release` (lto, strip) перенесён в корень воркспейса; `install.ps1`/`install.sh`, тест `guard.test.mjs` и `bundle-context-toolkit.mjs` берут бинарь из корневого `target/release`, а не из соседнего репозитория. Остальной текст раздела написан до объединения и говорит об Инструментах контекста как о соседнем проекте.

**Что известно из кода и README Инструментов контекста (прочитано, не запускалось).** Один нативный Rust-бинарь для тех же клиентов (Claude Code, Claude Desktop, Antigravity, DeepSeek Harness): хуки `guard` и `backslash`, `context-toolkit check`, `context-toolkit setup`, `context-toolkit doctor` и `context-toolkit report`. Две последние команды печатают JSON с `"schema": 1`, и в README прямо сказано «для оболочек вроде Loadout». `setup` пишет в те же файлы, что и Loadout (`settings.json`, `CLAUDE.md`, `ccd-session-presets.json`, `hooks.json`, `cordis.patch.yml`), с копией в `backups/<имя>.<время>.bak`, и отказывается работать, пока запущен Claude Desktop (тот перезаписывает пресеты). Хуки Инструментов контекста Loadout уже видит: метка `ctxkit` в конвейере хуков у Claude Code, Antigravity и DeepSeek.

**Три способа встроиться.**
- **A. Loadout читает Инструменты контекста.** Кнопка в Докторе «Спросить Инструменты контекста»: окно запускает `context-toolkit doctor --json` по фиксированному пути (`%USERPROFILE%\.local\bin\context-toolkit.exe`, таймаут 5 с, ответ проверяется по форме, `schema` должна быть 1) и добавляет его находки («субагенты не вызываются: хук, модель, агенты, блок правил») к своим; `report --json` даёт счётчики для Радара. Запуск чужого бинаря только по явной кнопке, как проверка MCP (§5). Связанности по коду нет, это самый дешёвый путь.
- **B. Инструменты контекста используют `loadout-core`.** Ядро не зависит ни от Electron, ни от окна (крейт-библиотека, модель и сканер пяти клиентов, безопасный конвейер записи с хеш-блокировкой, бэкапом, атомарной записью и журналом, прошедший два независимых аудита). Инструменты контекста могли бы брать из него «что установлено у клиента» вместо своих чтений конфигов и общий конвейер записи вместо своего кода бэкапов в `setup.rs` (1787 строк). Для этого нужны git-зависимость между репозиториями и согласованные лицензии (у Loadout тогда был `UNLICENSED`, у Инструментов контекста есть `LICENSE`; позже весь репозиторий стал MIT).
- **C. Подкоманда `context-toolkit loadout scan|serve`** с тем же бинарём. Один артефакт установки, но Инструменты контекста перестают быть «одним маленьким бинарём» и тянут все зависимости ядра (`notify`, `yaml-rust2`, `toml_edit`, `jsonc-parser`).

**Решение владельца (после первой версии этого раздела): Инструменты контекста встроены в приложение**, чтобы пользователь мог установить их, применить и видеть эффект (§10.8). Это вариант A, усиленный тем, что бинарь Инструментов контекста лежит прямо в составе приложения (`resources/context-toolkit.exe`): Loadout запускает именно его, а не то, что окажется в PATH. B (общий крейт) и C (подкоманда) остаются на потом.

**Первоначальная рекомендация:** A после M5, B позже, когда конвейер записи отстоится; C не делать. Гонку между двумя писателями (`context-toolkit setup` и Loadout правят один `settings.json`) закрывает уже существующая хеш-блокировка Loadout: запись с устаревшим хешем отказывает, а сторож показывает правку Инструментов контекста как обычное изменение.

**Заготовки, сделанные заранее.** Версия протокола `serve` (`"protocol": 1`) в `ready` и `status`: оболочка (окно, Инструменты контекста) сверяет её и не работает с несовместимым ядром; ядро и бинарь `loadout` не зависят от окна; имена бинарей разные (`loadout`, `context-toolkit`), каталоги бэкапов разные (`%APPDATA%\loadout-app\backups` и `backups/` Инструментов контекста): общего не затирают. Знак и строка заголовка (§10.9) на Инструменты контекста не завязаны.

**Открытый вопрос владельцу (закрыт: Инструменты контекста встроены, репозитории объединены, см. выше).** «Добавить в программу ctxkit» я понял как интеграцию A/B. Если имелось в виду другое (например, положить само приложение Loadout в репозиторий ctxkit или сделать его частью установщика ctxkit), решение меняется: тогда в первую очередь надо согласовать лицензии и каталог сборки, а A и B остаются на потом.

## 12. Что осознанно не сделано в концепте

Записано на этапе концепта, до кода (код начался с M0, итоги в §10). `shortcut:` нет `npm install`, нет Electron-скелета и cargo-проекта — это концепт, код начинается с M0. Метки «гипотеза» из §2 не проверены чтением значений секретных конфигов: имена файлов, секций и ключей смотрел, токены не трогал. Проза документа не прогонялась через humanizer. В макете имена сущностей реальные с этой машины, а состояния («сломано», «секрет открыт», «отстаёт») подобраны для демонстрации. Известные недоделки макета: нет ловушки фокуса в палитре и `aria-activedescendant` у её поля; часть статических значений вставляется без `esc` (данные не приходят снаружи).
