# Loadout — concept

[English](CONCEPT.en.md) · [Русский](CONCEPT.md) — the Russian text is the source; this is its translation (UI strings quoted in the text are translated too, the application itself is in Russian).

> What is loaded into your agents: plugins, MCP, skills, hooks, agents, rules. One screen for all clients.

Status: concept. There is no application code, only this document and a clickable mockup `mockup/index.html`.
Labels in the tables: **[verified]** — seen on this machine: file, directory and key names, plus one entry each without secrets (`installed_plugins.json`, the header of one `SKILL.md`); values from configs with tokens were not read; **[hypothesis]** — not verified, to be confirmed on fixtures in M0.

## 1. Problem and goal

Agent entries are scattered across five clients and dozens of files in different formats (JSON, TOML, YAML, directories with `SKILL.md`). The question "where is glidehand installed and is it enabled in Codex?" can only be answered by hand.

Goal: to see at a glance **what is installed, enabled and broken where**, and to manage it safely.

Non-goals (v1):
- Managing cloud connectors at the account level (connecting/disconnecting in claude.ai or ChatGPT). There is no public API; details and what can still be done are in §5.1.
- Installing plugins from marketplaces. That is up to the clients themselves.
- macOS and Linux. Paths are abstracted from the start, but only Windows 11 is tested and built. WSL projects (Codex's `config.toml` has `\\wsl.localhost\...`) come after v1.

Important observations from which the design grew:
1. **One package — several clients.** The plugin `ai-playbook` carries `.claude-plugin`, `.codex-plugin` and `.antigravity-plugin` at once **[verified]**. So one logical entry lives in the clients as separate instances. The main screen is built as an "entry × clients" matrix.
   **The type of instances may differ:** glidehand is enabled in Claude Code as a plugin (`enabledPlugins`), and in Codex and Antigravity it is connected as an MCP server **[verified by the verifier, by key names]**. Therefore `kind` is a property of an instance, and a row's `logicalKey` groups by name across types. The matching rules ("plugin X" ↔ "MCP X") are an M0 task.
2. **Duplicates and drift already exist.** In `installed_plugins.json`, `skill-creator@claude-plugins-official` is recorded twice: scope `user` and scope `project` (with `projectPath`) **[verified]**. The `version` field differs between the two records (short git hashes) — seen on this machine. Separately, `skill-creator` is also present in both `~/.codex/skills` and `~/.codex/skills/.system`.
3. **A dump of backups.** `~/.codex` and `~/.gemini/config` each contain about 20 foreign `*.bak` files. We add nothing there; we have our own storage.
4. **Secrets next to settings.** `~/.claude.json` contains the key `oauthAccount` **[verified, key name]**. That MCP configs keep tokens in `env` is a **[hypothesis]**; I did not read the values. Masking is a requirement, not an option.

## 3. Unified model

```
Entity {
  id            stable hash(client, scope, kind, name, source.file)
  logicalKey    key for a matrix row: package/server name, normalized
  kind          plugin | mcp | skill | hook | agent | command | rule | marketplace | memory | connector
                (a property of an instance: glidehand is a plugin in one client and mcp in another)
  client        claude-code | claude-desktop | codex | antigravity | deepseek
  scope         user | project(path) | plugin(origin) | builtin | cloud
  origin        { plugin?, marketplace?, file, pointer }   // pointer: JSON Pointer / TOML key / line
  state         on | off | broken | shadowed | stale | unknown
  version       string | gitCommitSha
  capabilities  { toggle, remove, edit, copyTo[] }          // what may be done with this instance
  usage?        { lastSeen, count }                         // if the client writes it
  fingerprint   content hash (SKILL.md, manifest) for finding "the same thing in another client"
  masked        fields that are hidden
}
```

States:

| state | meaning | how we find out |
|---|---|---|
| `on` / `off` | enabled / disabled by the client | `enabledPlugins`, the MCP disabling mechanisms from §2, `[plugins.*] enabled`, … |
| `broken` | the MCP command is not found, `installPath` does not exist, a hook references a missing script | `which` / `exists`, without running anything |
| `shadowed` | an entry of the same name is overridden by another scope | the specific client's merge order |
| `stale` | version/hash differs from other clients or the marketplace | comparing `fingerprint`/`version` |
| `unknown` | format not recognized | the adapter keeps the raw fragment and **does not touch** it |

Adapter rule: **unknown keys are preserved as is on write.** The formats are unofficial and change, so each adapter has a `schemaVersion`, and to anything unexpected it responds with `unknown` rather than crashing.

## 5. Write safety

Everything can be read, writing is by levels. The level is enabled in settings, off by default.

| Level | What is allowed | Version |
|---|---|---|
| R0 | read only | v1 / M1 |
| R1 | enable / disable | M3 |
| R2 | edit, copy between clients, move to trash, apply profiles and the built-in ctxkit | M4, §10.8 |

The pipeline for any write:
1. **Plan**: the core builds a set of edits and a diff, writes nothing.
2. **Preview**: the UI shows a diff for each file, the user confirms.
3. **Is the client running?** We check the process (Claude Code, Codex, Antigravity, dsh). If so — a warning that the client may overwrite the file with its own state, and an offer to wait.
4. **Optimistic locking**: the file hash before the plan and before the write. If it does not match — rebuild the plan.
5. **Backup** into `%APPDATA%\Loadout\backups\<time>\` with a manifest (source path, SHA-256). We do not create foreign `.bak` files.
6. **Atomic write**: a temporary file alongside + rename. TOML is edited via `toml_edit` (preserves comments and order), JSON by a targeted CST edit rather than rewriting the whole file.
7. **Verification**: re-read and make sure the result equals "original + plan" and nothing else changed.
8. **Rollback** with one button from the journal. Deletion = a move to the Loadout trash, not `rm`.

Secrets:
- By default the core returns values **masked**. `env` values and MCP headers are not output at all, only key names; the files from the "Secrets of other clients" row in §2 are not read. Hook arguments and commands are free text. Two audits in a row found new bypasses of a blacklist (by word, by form), so the approach is the opposite, a **whitelist**: only what is recognized as harmless remains in the output, everything else is replaced with `<masked>`. Shown: flag names (`--port`, `-y`, PowerShell parameters from a short list), numbers up to five digits, paths (rooted or ending in a file name of a known type, without `@ ? = ; & | + ! *`, a colon only in `C:`, no segment looks like a secret: so a base64 string with slashes does not pass as a path), URLs (a known scheme, verified host and port, without userinfo such as `user:pass@` and `token@`, query, `;parameters`, token-like, JWT and %-encoded path segments), package names with a version (`rea-agents@6.8.0`) and the package name after `npx`/`uvx`, file names of known types, the executable in the command position (lowercase only), a small set of typical words (`node`, `bash`, `mcp`, `serve` …) and operators with redirections. Always hidden: the value after a secretly named flag (`--token`, `--auth`, `--pat` …), `NAME=value`, JSON and PowerShell hash tables in an argument, `-pPASSWORD`, `/P:…`, unknown short flags. Nested command lines (`bash -c "…"`) are parsed recursively up to three levels, quotes are accounted for, including `\"`. The label and `logicalKey` of a hook are built from already masked tokens, while `type`, `timeout`, `matcher`, versions, hashes, skill and hook event names, the plugin scope and `env` key names pass alphabet and shape filters (token-like words are discarded); a skill's `description` passes masking of token-like words. From all string fields, including pointers and names, the home directory path is scrubbed (case-insensitively and at a word boundary; the forms `C:\…`, `C:\\…`, `C:/…`, `/c/…`, `/mnt/c/…`, `/home/<name>`, `\\localhost\c$\…`). The cost: part of the useful text (positional words, flag values) is shown as `<masked>`; the UI shows the full command only on an explicit action. Known limits: a secret in a skill description that does not look like a token (an ordinary phrase) is not masked; the short 8.3 name is computed by a pattern (the first six characters and `~1..3`), not from the file system; in MCP `args`, a word from the harmless-words list (`debug`, `main` …) after a secret flag is still hidden, but after a *non-secret* one it is shown.
- "Show" is by hold: the value lives in the UI only while held.
- No telemetry and no network. The application works offline and makes no requests to marketplaces.

Running third-party commands:
- Checking an MCP server ("start it and ask for tools/list") **executes the command from the config**, so it is done only via an explicit button on a specific server, with a 5 s timeout and in a separate process. There is no bulk check.

## 6. Architecture

```
┌────────────────────────── Electron ──────────────────────────┐
│ renderer (React + TypeScript + Vite)   — UI only              │
│   ▲ typed IPC (contextBridge, allow-list)                     │
│ main  — windows, menu, tray, file dialogs, process watcher    │
│   ▲ stdio: JSON-RPC, lines separated by \n                    │
└───┼───────────────────────────────────────────────────────────┘
    ▼
loadoutd (Rust, sidecar)  ──  loadout-core (library)
   adapters/{claude_code, claude_desktop, codex, antigravity, deepseek}
   model · scan · diff · plan · backup · mask · watch (notify)
```

**The Rust ↔ Electron boundary: a sidecar over stdio, not napi-rs.** Reasons: a parser crash does not take down the window; the native module does not have to be rebuilt for every Electron version; the same binary works as a CLI (`loadout scan --json`) and in tests. The cost is serialization, but the volumes here are hundreds of entries, so it is not a bottleneck.

Choice of technologies (driven by convenience, not by requirements):
- Renderer: React + TypeScript, `@tanstack/react-virtual` for lists, Zustand for state. Nothing heavier.
- Rust: `serde`/`serde_json`, `toml_edit`, `serde_yaml` (YAML is read-only in v1), `notify`, `rayon`, `sha2`, `jsonc-parser`.
- A third language is not needed. We do not add Python/Go.
- Packaging: `electron-builder`, an NSIS installer for Windows. The sidecar sits alongside, its path is hardcoded, not taken from PATH.

Electron security: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, a strict CSP without `unsafe-eval`, no remote URLs, IPC only via an allow-list, file names from the UI are validated by the core (writes only to the known adapter paths).

Repository structure layout:
```
Loadout/
  crates/loadout-core/     model, adapters, diff, backup
  crates/loadoutd/         sidecar (JSON-RPC)
  app/{main,preload,renderer}/
  fixtures/                synthetic configs shaped like real ones (we do not store snapshots from a live machine: they contain secrets and names)
  docs/CONCEPT.md
  mockup/index.html
```

## 7. Performance

Targets, **not measured** (to be measured in M1):
- cold scan of all clients: under 500 ms on this machine;
- idle: 0 % CPU, the window in the background is not repainted;
- RAM at idle: up to 150 MB.

How we get there:
- The scan is parallel (`rayon`); for `SKILL.md` we read only the head (up to 4 KB) for the frontmatter.
- A cache "path + mtime + size → parsed entry"; only what has changed is re-read.
- The `notify` file watcher covers only the known configs and skill directories. **We do not watch the `plugins/cache`, `sessions`, `transcripts`, `projects` directories or `*.sqlite`**: they are huge and noisy. Debounce 200 ms.
- List virtualization, otherwise a matrix of a thousand rows lags.
- The matrix is rendered without a per-cell animation.

## 8. Visual language: Dracula + HUD

Palette (official Dracula):

| Role | Color |
|---|---|
| background | `#282a36`, panels `#21222c`, lines `#44475a` |
| text | `#f8f8f2` |
| muted text | **`#9aa5ce`**, not `#6272a4` |
| accents | cyan `#8be9fd`, purple `#bd93f9`, pink `#ff79c6` |
| states | green `#50fa7b` (on), orange `#ffb86c` (stale), purple `#bd93f9` (shadowed), red `#ff5555` (broken; in the mockup the glyph is lighter, `#ff6e6e`: on the panel 5.80, in the selected cell 4.76, on hover 5.13; at the low point of the pulse with `opacity .7` it is 3.04–3.50, this is an icon with a label, and its threshold is 3:1), gray (off), light blue (cloud) |

**The contrast is calculated** (WCAG, the formula from the specification): the classic "comment" color `#6272a4` on `#282a36` gives **3.03:1**, which does not pass AA for text (4.5 is needed). For text we use `#9aa5ce` (5.86:1). `#6272a4` is suitable only for borders and decoration. Red `#ff5555` on the background is 4.53:1, which barely passes, so red always comes with a glyph and a label.

HUD effects are only the cheap ones:
- corner brackets on panels (pseudo-elements); there are **no** scanlines (a linear horizontal ripple over the window) and no logo flicker: they were removed in M4 on the owner's remark, because in screenshots the hatching read as a ripple;
- glow on accents via `box-shadow` / `text-shadow`;
- a radar with a rotating beam (`conic-gradient` + `transform: rotate`, runs on the compositor and does not trigger layout);
- a state pulse (`opacity`), a short "loading" animation at startup (up to 600 ms), counters with a smooth number ramp-up;
- no WebGL/canvas in v1. This is a matter of GPU usage on a shared machine.

Effects control: the setting **FX: off / light / full**. With `prefers-reduced-motion`, "off" is enabled automatically. If the window loses focus or is minimized, animations are paused.

Accessibility: state is conveyed not only by color but also by glyph shape (`●` on, `○` off, `◐` mismatch, `◒` shadowed, `☁` cloud only, `✕` broken, `–` none); we do not use `#44475a` as a text or glyph color on the panel background (contrast about 1.7); for "none" we take `#6272a4` only as decoration next to a label; a visible focus ring; the matrix is `role="grid"`; full keyboard operation.

What is in the repository: a Rust workspace (`crates/loadout-core`: model, masking, adapters; `crates/loadoutd`: the `loadout` binary), synthetic fixtures `fixtures/home`, 24 tests. Usage: `loadout scan [--json] [--pretty] [--home PATH] [--client claude-code|codex]`. Read-only.

Measurement on this machine (release, a single run): `scan --json` of two clients takes 26–44 ms including process startup, 191 entries, about 72 KB of JSON. The §7 target was 500 ms for all clients; there are no statistics, this is a single measurement.

What the hypotheses showed on real files:
- **A plugin's `scope` is not only `user` and `project` but also `local`** (two entries). The enabled flag for `project`/`local` lives in the project settings, M0 does not read them, so such plugins are shown as `unknown` (29 of 32 `unknown`). The other three `unknown` are `user`-scope plugins without an entry in `enabledPlugins`.
- **The owner's stash of disabled MCP servers** lies in two keys of `~/.claude.json`: `_disabledMcpServers` and `_mcpServersDisabled`, 7 servers in total, with a note string `_note` next to them. This is not a standard Claude Code mechanism (per the owner's own note, a server is brought back by moving the entry into `mcpServers`), but it works as a model for the Loadout trash. The scanner shows them as `off` and skips keys starting with `_`.
- **claude.ai connectors:** `claudeAiMcpEverConnected` gives three names, and `disableClaudeAiConnectors: true` switches them to `off` with a single key. These are levels C0 and C1 from §5.1, and they work on data.
- **Hooks** in Claude Code and Codex share one format `{event: [{matcher?, hooks:[{type, command, timeout}]}]}` (3 and 9 events) **[verified]**. However, **matching hooks between clients by label was not confirmed on real data**: there are no common `logicalKey` values. In Claude Code these are `ctxkit` and `pull-skills`; in Codex all nine events go through a single wrapper script `~/.orca/agent-hooks/codex-hook.cmd`. Matching by label works only on the fixture (`guard`). For real hooks, matching has to be done by wrapper and directory (`~/.orca/agent-hooks` also occurs in DeepSeek: the `orca-agent-hooks` entry in `cordis.patch.yml`); this is M1.
- **One logical object in different clients** works on live data: glidehand is a plugin in Claude Code and an MCP server in Codex, harnio is a plugin in both, `bash-tui` and three more skills exist in both.
- **Skills:** Claude Code 16, Codex 32 (27 + 5 from `.system`), as the checker found.

What M0 caught in itself, in two passes:
1. A run on real configs (the check "values of secret keys do not occur in the output") found a leak: a header passed as a single argument (`--header "Authorization: Bearer …"`) was not masked.
2. An independent `checker` audit broke masking in ten more forms: `-e GH_PAT=…`, `--env NAME value`, `curl -u user:pass`, JSON in an argument, `-H Name:value` without a space, `--auth`, a connection string `Password=…`, a key in a URL path, `OAUTH_…`, `--pat`. Worse, the secret got into the **hook name and `logicalKey`**, because the label was built from the raw command, and `mask_line` split the line on spaces and did not know about quotes. The first fix was a tokenizer with quotes and rules based on the shape and appearance of the value, with the hook label built from masked tokens. The twelve forms from the audit and the quoting cases went into the tests (caveat: the key in a URL path in the test is 30 characters long; a short key in a path, up to 24 characters, is not masked). A repeat pass found more bypasses: a nested command line as a single argument (`bash -c "tool --token X"`, including with `;` and `=`), a secret with a space (`--token="a b"`) in the hook label, positional passwords (`mysql -pX`), JSON inside an argument, passwords in a URL with `?`, `#`, `/`, a home path in the form `C:\\Users` inside JSON, a UNC path. Answering each of these with a blacklist would be yet another patch, so masking was **rewritten as a whitelist** (§5). Along the way, the Cyrillic test caught a panic in `scrub` itself: slicing a string at a byte offset inside a letter (fixed).

The third audit (already against the whitelist) still found bypasses: a token in a URL userinfo without a colon (`git+https://ghp_…@github.com/…`), a nested string whose first word is a path (`bash -c "/usr/bin/tool secret"`), base64 with slashes taken for a path, a URL scheme and host without a check, values after non-secret flags (`-p`, `--passphrase`), redirects (`2>/dev/null secret`), fields outside `mask.rs` (names, descriptions, scope, `env` keys), mixed separators and short 8.3 names in the home path. All of it is closed in code and tests; on real data the whitelist now shows more useful information (package names after `npx`, script paths) than the second version did, and `<masked>` remains in the output 3 times. A fourth audit was not run: there is no guarantee that "there are no bypasses"; this is a defense that has been checked three times and broken each time, so M1 needs fuzzing and a list of forbidden forms from the audits in CI. Along the way the home directory path is scrubbed from all string fields, including pointers, case-insensitively and in the Git Bash, WSL and `/home/<name>` forms.

After the fixes, of the 23 secret values checked on real configs (now including values after secret flags in args), one remained in the output, and it is not a secret: the `N8N_API_URL` URL, which matches the address of the server itself. This is a check against this machine's configs, not a proof: the list of forms in the tests was invented from the bypasses found, and new bypasses are possible. Therefore in M1 masking remains under fuzzing and audit.

Decisions on the audit remarks: a plugin's `stale` now applies only when versions differ **within the same scope**; a different version in `project`/`local` gives a note but not a state (on real data `stale` became 0, previously it was 2). JSON Pointer now escapes `~` and `/`, and TOML keys in pointers are uniformly quoted where necessary. Deliberately not fixed: a password in a URL with `/` inside, because by the standard such a password must be encoded.

The items promised for verification in M0 and what became of them: the `dsh-mcp-client` schema (the package is unavailable, the junction is broken, §11), `deniedMcpServers` (the key is absent from the owner's `settings.json`), the `[apps.*]` sections in Codex (absent on the machine, the official schema was not read): all three are unverified and moved to M1 (closed in M1, §10.2); the storage location of the `/mcp` toggle is indirectly confirmed (`projects.*.disabledMcpServers`, §2).

Deliberately not done in M0 (`shortcut:`): project settings (`.claude/settings.json`, `settings.local.json`, `.mcp.json`), entries brought in by the plugins themselves (their skills, hooks, MCP), `skillOverrides`, `projects.*.disabledMcpServers`, comparison of duplicates across scopes (Doctor), symbolic links, paths longer than the Windows limit. The file watcher and writing are M2 and M3.

### 10.2 M1 results (the application and five clients)

What exists: the Rust core reads **five clients** (Claude Desktop, Antigravity and DeepSeek were added), and the Electron application `app/` (electron-vite, React, TypeScript) runs the core with the command `loadout scan --json` and shows the Matrix, Radar, Hooks, Doctor, Command Palette and Inspector. Read-only.

**The sidecar decision.** In M1 `serve` (JSON-RPC over stdio) is not needed: a full scan takes 55 ms, and the file watcher is M2. The main process does `execFile` on the binary at a fixed path, and the response is validated by shape. `shortcut:` JSON-RPC and push updates are added together with the file watcher.

**Row and cell aggregation** (it was not in the mockup, and on real data it is decisive). Rows are grouped by class, not by `kind`: a plugin and an MCP with the same name are one row (`glidehand` is a plugin in Claude Code, an MCP in Codex, Antigravity and DeepSeek), while a marketplace with the same name is another row. A "client × row" cell can hold many entries. The primary one is chosen by scope: `user`, then `local`, `plugin:*`, `profile:*`, `builtin`, `project:*`, `cloud`; a `+N` counter sits next to it. This way dozens of project entries of a plugin do not hide its user entry. Rows where all cells are `unknown` (the enable flag lies in project settings) are hidden by default with a checkbox; Doctor counts them. Hooks are grouped by label, and wrapper hooks of one program (`~/.orca/agent-hooks/codex-hook.cmd`, `dsh-hook.cmd`) fall under a shared key `orca-agent-hooks`. Nine Codex events give one row with nine entries.

**What was newly found out on the machine.**
- Antigravity: `mcp_config.json` is `{mcpServers:{name:{command,args,env?}}}` with no "disabled" flag (in the M0 mockup it was invented); `hooks.json` is `{group:{Event:[{matcher?,hooks:[…]}]}}`, that is, the Claude Code format one level deeper; plugins are `config/plugins/<directory>/{plugin.json, mcp_config.json, skills/}`.
- Claude Desktop: in `claude_desktop_config.json` only `mcpServers` count as entries (`preferences` are not entries).
- DeepSeek: `cordis.patch.yml` is read by the `yaml-rust2` parser, the tag `!!js process.cwd()` does not break parsing and is not executed; profiles (`profiles/<name>/cordis.patch.yml`) are read separately (two of them contain the `ponytail-dsh` plugin); hooks go through the `dsh-hooks-*` entry → `configPath` (read only inside the home directory, `..` is rejected).
- The schema of `@deepseek-ai/dsh-mcp-client` (npm `0.0.1-rc.1`): `transport: 'stdio' | 'streamable-http'`, `serverName` (`[A-Za-z0-9_-]{1,32}`), for stdio `command, args, env, cwd, toolCallTimeoutMs, failOnStartupError`, for http `url, headers`. There is no `enabled`/`disabled` flag; a plugin entry is edited "hot": according to the package description, changing an entry disconnects and reconnects the server without restarting the host. The `reconnect` key from the owner's file does not exist in this package version: the file is newer than the package.
- `deniedMcpServers` (per the Claude Code documentation, `managed-mcp.md`): works in any settings file, entries of the form `{serverName}`, `{serverCommand: […]}`, `{serverUrl}`; claude.ai connectors (`claude.ai Slack`) are also blocked by `serverName`. Matching by `serverName` is implemented; the key is absent from the owner's `settings.json`, verified on a fixture.
- Codex `[apps.<id>] enabled` (Codex configuration reference): the key is documented, `apps._default.enabled` is the default value. Reading is implemented; the owner's machine has no `[apps]` sections, verified on a fixture.
- Downloading the dsh package with `npm pack` showed that the package calls MCP servers directly (`command` from the entry): this confirms that `command`/`args` of dsh entries must be masked the same way as for other clients (they are masked through the shared `mcp_detail`).

- masking: `package@version` let a random token through (`bot@7a9F…`, `admin@123`) — now only a semver or a release tag counts as a version; unknown flags `-pw`, `-pass`, `-Password` did not hide the value — now they do; a header as a separate token (`X-Token:` + `48213`) — is hidden; `--pin`, `--otp`, `--code` were added; hexadecimal segments of 20 characters or more and words of letters and digits of 32 characters or more are treated as a secret; base64 split by slashes (`/K7MDENG/bPx…`) no longer passes as a path; a package name after `npx` counts as a name only if it is not preceded by a flag with a value (the canary found `--header hunterpw`);

### 10.3 M2 results (file watcher, sidecar, Doctor)

**The M1 tail found while preparing M2.** After the final audit fixes nobody looked at a real scan: the `real_machine` test checked only for leaks, and "0 of 25" could have come from the scanner silently finding nothing. Now the test has a lower bound (no warnings, every found client has entries, `cordis.patch.yml` yields the dsh MCP, names are not hidden). The check immediately found two defects of the audit: entries of the Codex directory `app-69f0dc45…` turned into `<masked>` under the new token-word scrubbing and merged into one row (now names taken from the file system are marked `fs_named` and are not hidden), and in project path pointers `~1` glued the whole path into one "token" (now `~` is a separator).

**The sidecar.** `loadout serve [--home PATH]`: JSON-RPC over stdio, one message per line with a buffer flush. Methods: `scan` (rereads the disk), `snapshot` (the last state), `status`; notifications `ready` and `changed`. There are no methods with paths. `changed` carries only entry ids (`added`, `removed`, `changed`), the flags `warningsChanged`, `factsChanged` and a sequence number `seq`; there are no raw paths or values in the event, and a test verifies this. A broken (non-UTF-8) line on stdin gets an error response, the process does not exit. EOF on stdin terminates the process within seconds (otherwise on Windows the core would outlive the window). `loadout scan --json` works as before.

**The file watcher (`notify` 8.2, stable; `9.0.0-rc` was not taken).** Directories are watched non-recursively with a file-name filter (replacing a file by renaming breaks the watch on the file itself, but not on the directory); recursively only the skills directories. `plugins/cache` (except Codex's `openai-curated-remote`: there the entries are subdirectories), `sessions`, `projects`, `*.sqlite`, `*.jsonl`, `node_modules` are not watched; `*.bak*`, `*.backup`, `*.recovery` are significant only as direct children of the four client directories (Doctor facts are counted from them). The set of paths is rebuilt after every scan, even without meaningful changes: files from which entries are built (for example, the dynamic `configPath` of dsh hooks) add their parents. A directory created after the core started (a client installed later, `skills` appeared) is noticed: the appearance, removal and renaming of the permanent directory itself is significant, and for a directory that does not exist yet the nearest existing ancestor is watched (`.gemini` for `.gemini/config`, `AppData/Roaming` for Claude Desktop, otherwise home), and the creation of intermediate directories is also significant. A subscription to a deleted directory is dropped immediately, even if it was at once recreated with the same contents (`git checkout`: the scan is the same, there is no `changed`, but the old subscription is dead); after any watcher error all subscriptions are recreated. Debounce is 300 ms, but no longer than 2 s under continuous events; the deadline is checked at the start of every step, so a stream of requests does not postpone a scan. Any watcher error is a reason to reread the disk. The directory of dsh junctions (`profiles/node_modules/@deepseek-ai`) is not watched: the fact about broken links will be refreshed on the next scan triggered by any other event, or manually. The main point: after the debounce the scan is compared with the previous one, and `changed` is sent **only on a meaningful difference**, so the constant rewriting of `~/.claude.json` does not make the window flicker.

**Figures (release, a single measurement on this machine with a Claude Code session running).** Over 60 s of idle: 156 ms of CPU time (0.26% of one core), 10 MB of memory, of messages only `ready`, `changed` not once. A repeat measurement after the rules from the final audit (30 s, 8.8 MB): 0 ms of CPU time. The §7 goal "idle is about 0% CPU" is met. A full scan is 55 ms.

After a restart the window catches up with changes made during the pause. A push (`changed`) goes through the same shape validation as a response to a request; the page receives only data, without `ipcRenderer`. Data in the window changes **in place**: no "loading" screen, the selection is held by entry id rather than by number, and focus does not drop. Changed entries are marked with a Δ icon and a frame (not only by color, animation only with FX) for 8 seconds. The footer shows the time of the last update. In the packaged build `LOADOUT_*`, `ELECTRON_RENDERER_URL` and the `APP_QA` mode itself are always ignored (previously `APP_QA=1` let them through), and the dev server address is compared by origin, not by string prefix. ### 10.4 M3 results (write level R1)

**Scope.** Only boolean flags that already exist in the client formats are toggled: Claude Code — `enabledPlugins[key]` and `disableClaudeAiConnectors` (one key for all connectors at once; the plan shows this as the number of affected entries); Codex — `plugins.*.enabled`, `mcp_servers.*.enabled`, `apps.*.enabled`. On the owner's machine this is 63 entries. Where "disable" means removing or moving an entry (MCP in `~/.claude.json`, Antigravity, DeepSeek, Claude Desktop), there is no toggle, and the inspector states the reason (the `toggleWhy` field): this is the Loadout trash and editing, that is, M4.

**How it works.**
- Core (`write.rs`, `edit.rs`): entry → `target` (the real file and the raw key, `#[serde(skip)]`, never goes outward). The RPC accepts only the entry id and the desired state, and the core rescans and finds the target itself; there are still no methods with paths. Writing is allowed only to `~/.claude/settings.json` and `~/.codex/config.toml` (the list is checked both on write and on rollback: the manifest lies in the user's directory and is not considered trusted).
- The edit is surgical: JSON — via the `jsonc-parser` AST, only the `true`/`false` literal changes (or one entry is added with the file's indentation), TOML — `toml_edit` 0.22 (the same copy as in `toml 0.8`), comments and order stay intact; BOM and CRLF are preserved, a repeated key is edited at the last occurrence (this is how `serde_json` reads it). In a file with mixed CRLF/LF and in an empty object with a comment, the edit is refused.
- Pipeline (§5): the file hash in the plan → check at `apply` and once more before the write → backup (`before`) and manifest with `sync_all` → a temporary file `…loadout.tmp` next to it and `rename` → re-read and compare with the plan. Rollback is the same write from the backup, only if the file hash equals "after" from the manifest, otherwise it is refused. The backup directory is passed as the argument `serve --backups`; without it `apply`, `journal`, `rollback` refuse (`plan` always works).
- The preview contains the file (with `~`), the pointer, `was → became` values, and affected entries; there is no file content and no context lines (test with `FAKE-SECRET`).
- Window: the R0/R1 level is stored in the application profile (R0 by default) and is checked in main before every `apply`/`rollback`; raising to R1 is confirmed by an OS dialog (the page cannot press it). Before the preview, main checks via `tasklist` whether the client is running (a warning, not a prohibition). Space on the selected cell or a button in the inspector → preview → "Apply"; a "Journal" section with rollback; `changed` arrives immediately after the write, without waiting for the file watcher.

**Checks.** Core: 12 integration write tests on copies of the fixtures (round trip byte by byte, stale plan, rollback after a foreign edit, insertion of a missing key, connectors with a shared key, denial by name, chain of rollbacks, `apps`, absence of content and paths in responses, path substitution in the manifest) and 9 `edit.rs` tests; three `serve` tests over JSON-RPC. ### 10.5 M4 results (R2: trash, edit, copy, profiles)

**Decision on the trash.** A removed entry lies in the Loadout storage (`<backups>/trash/<id>.json`), and not under a new key in a foreign file: it has not been verified anywhere that Claude Desktop and Antigravity preserve unknown keys on rewrite, and a lost key would mean a lost entry. In the scan such an entry is visible as `off` with the same file and pointer, so its id, the selection in the window, the journal, and the profiles do not change. "Enable" is a direct insertion of the saved text back. "Delete" from §5 is precisely the removal to the trash; there is no separate delete operation. The owner's stash (`_disabledMcpServers` in `~/.claude.json`) is enabled by a move inside the file; rollback of this enabling with the file unchanged returns the file from the backup (the entry is in the stash again), and if the file has changed since, the reverse operation removes the entry to the Loadout trash (it is not returned to the stash then). For an entry from the stash the pointer changes (`/mcpServers/x`), so the id after enabling is different, and rollback finds the entry by client, kind, and name.

**What is possible (level R2, besides flags).**
- Removal and return of MCP without the "disabled" flag: Claude Code (`~/.claude.json`, user scope), Claude Desktop, Antigravity (`mcp_config.json`) — by JSON value, the other bytes of the file are the same (verified: the first, middle, last, and only entry, CRLF, the return gives a semantically equal file); DeepSeek — by lines of `cordis.patch.yml` (§ below).
- Edit: the `command` and `args` of an MCP as a whole (the window does not receive the old values, they are masked in the list). The new command and arguments in the preview and the journal go through the same masking (`--token X` → `<masked>`), and go into the file as entered; `env` and headers do not change.
- Copying an MCP between Claude Code, Claude Desktop, Antigravity, and Codex with JSON ⇄ TOML format conversion (`headers` ⇄ `http_headers`, `type: http` is added for Claude Code). The values of `env` and headers (secrets) travel only inside the core: the RPC accepts the id of the source and of the target client, and the preview contains the names of the `env` keys, what is not transferred, and the masked command. An occupied name (in the file or in the recipient's trash) is a refusal.
- Profiles (`<backups>/profiles.json`): a name, a set of "client, kind, scope, name → enabled/disabled". They are created as a snapshot of the current state of plugins and MCP (connectors are not included: one key for all), and edited with checkboxes. Applying is a batch: one preview for all differing entries, each with its own backup and journal row with a common batch number, "Roll back batch" rolls back everything starting from the last write. The batch signature (file hashes) is checked on apply, at the first error the batch stops, and what was done remains in the journal.
- Rollback of removed and returned entries is a reverse operation on the current file (`~/.claude.json` is rewritten by the client constantly, a hash check there would almost always refuse); rollback of flags, edits, and copies is returning the file from the backup while the "after" hash is unchanged.

**DeepSeek.** `cordis.patch.yml` cannot be parsed and assembled anew (the `!!js` tag, written by many installers), so removal and return go by lines (`yaml_edit.rs`): the position of an entry is taken from the `yaml-rust2` parse events (the start line of each entry of the `insert` list), the entry's lines are cut out together with the blank lines before it, and the installers' comment lines at zero indentation between operations stay in place. After the edit the result is parsed again and compared: the other entries are equal to the previous ones, this one is not (or is in place). If it does not match, anchors, aliases, flow style, or tabs — refusal, the file does not change. Verified: removal and return byte by byte on the fixture (including CRLF and a file without a trailing newline) and on a **real** file without the entry (dry `plan`: the structure of the file with the installers' comments at first did not pass the bounds check, this was fixed). A DeepSeek entry cannot be edited or copied.

**Levels.** R0 — read only, R1 — flags, R2 — trash, edit, copy, profiles. Each includes the previous ones. They are stored in the application profile, and checked **both in main and in the core**: main passes the core `maxLevel` in the same request as the write, and the core itself compares it with the level that the operation requires (the two-step scheme "asked for the plan, checked, applied" was vulnerable to a race; a `maxLevel` value outside `R1`/`R2` is a refusal, without the parameter only R1; main also checks the core protocol version, with an old core writing is disabled), and raising is confirmed by an OS dialog; the window checks substitute `dialog.showMessageBox` in main and check both consent and refusal (the `APP_QA` bypass was removed: the M3 audit found a hole on this path). A list in the header instead of a button: three levels are a choice, not a switch.

**Window.** The "Profiles" section (key 6), edit and copy dialogs, batch preview, "Roll back batch" in the journal, a level badge on operations. The write actions in the inspector stand in a **column**, not side by side (inspector 348 px). **Scanlines were removed** (a linear horizontal ripple over the window, `#scanlines`) together with the logo flicker: on the screenshots the hatching read as ripple, and the owner asked for it to be removed. The Impeccable detector on the live window of the build: 4 findings (logo glow, magenta and cyan neon on dark: a consequence of the requested Dracula palette), previously there were 5. The detector's own caveat: the window was hidden, so its pixel pass (contrast) read nothing, and there is no contrast verdict for these 4 findings (text contrast is checked by axe in e2e).

**Checks.** `cargo test`: core — JSON/TOML/YAML editing (14 `edit` tests, 7 `yaml_edit`), 31 write integration tests (and one ignored dry run on the real configs) (trash round trip with the same id, rollback after the client rewrote the file, stash, edit with journal masking, JSON⇄TOML copying and rollback, a profile as a batch and batch rollback, DeepSeek by lines, denial for plugin files), 17 `serve` tests over JSON-RPC; dry `plan` on the real configs (`real_machine_plans_are_dry_and_succeed`): 81 entries, five client files unchanged after the run. `vitest` 23. Window e2e: R0 refusal, refusal and consent in the level dialog, preview of removal to the trash, edit (no secret in the window), copying, profile, batch and batch rollback, actions in the inspector in a column, axe on profiles, measurement of horizontal scrolling. Screenshots `state/m4-*.png`. **The real home directory was never written to during development**: `apply` and `rollback` ran only on copies of the fixtures; `~/.claude.json` is the file of the development session itself, only `plan` ran on it.

**`checker` audit of M4 and what was done about it.** It found nine defects, reproduced on copies. They are fixed, each with a test:
1. **A DeepSeek profile silently applied one entry out of two.** The pointer (and with it the id) contained the entry number in the `insert` list; after the first was removed, the second "shifted", received a different id, and `apply_batch` skipped it, reporting success. Now the pointer contains the `id` of the entry from the file, and `apply_batch` skips only entries that were also absent in the preview, or already ready; an entry that disappeared in the middle of a batch is a stop with an error.
2. **R1→R2 raise by race.** main asked for the level with a separate `plan` and applied with a second call; between them the page could wedge in `profileSave`. Now main passes the core `maxLevel` in the same request as the write (`apply`, `rollback`, `rollbackBatch`, `applyProfile`), and the core refuses if the operation needs a higher level; without the parameter the core allows only R1. Rollback of an R2 operation also requires R2.
3. **Corruption of a DeepSeek entry.** A line of a block scalar starting with `#` was taken for a trailing comment and remained in the file as an orphan. Now the cut-out lines are parsed again and compared with the source entry, otherwise it is a refusal.
4. **The home directory path in the plan and the journal** (an entered command `<home>/bin/tool.exe`, copied arguments): now it is replaced with `~` by the same function as in the scan.
5. **Editing a command in CRLF JSON made the line endings mixed** (multi-line `args`): now the line endings are taken from the file. YAML: returning an entry to a CRLF file without a trailing newline also gets CRLF.
6. **A stale trash entry blocked removal** (the entry was added again by hand, the same id): now it is overwritten, the previous copy is kept in the manifest.
7. **Rollback of a return from the owner's stash** put the entry into the Loadout trash, and not back into `_disabledMcpServers`: with the file unchanged, rollback returns the file from the backup (the entry is in the stash again), and the reverse operation remains for cases when the file has changed since.
**Repeated `checker` audit (on commit 7f0841a) and what was done about it.** It found nine remarks. Fixed: (1) **with an old core the level check did not work** (it does not know `maxLevel`): main now checks the protocol version and with an old core disables writing, and `pack`, `dist`, and `e2e` rebuild the core themselves; (2) **overwriting a "stale" trash entry lost data**: now only identical text is overwritten, and different text is a refusal; (3) DeepSeek returned an entry **by old numbers** of the operation and wrote into a foreign operation: on removal an anchor is stored (the `id` of the neighboring entry), on return it is checked, otherwise a refusal; (4) `rollback_batch` at R1 rolled back a batch halfway: the levels of all operations are checked before the first rollback; (5) rollback of a removal looked for the entry **by name** and could return a foreign one: for entries from the trash it looks only by id; (6) DeepSeek entries without a simple unique `id` (or with `/` and a space) no longer get write targets (they remain positional and are not toggled), the pointer is escaped; (7) an invalid `maxLevel` (`R0`, `r2`, a number) is a refusal, not a silent R1; (8) the comments and this section are brought into line with the code; (9) `pack-check` closes only processes with its own profile and does not accept a `PACK_DIR` with special characters. Not fixed: rollback in reverse order enables DeepSeek entries in the order of removal (a forward order of enabling may swap entries, the file is then semantically the same but not byte by byte); the `app.asar` integrity-check fuse without a signature was **verified**: corrupting a byte in the archive header — the application does not start; corrupting a byte in the body of a file inside the archive — it starts (on Windows Electron checks the hash of the header, not of the content of each file, this is its limitation).

Deliberately not fixed (`shortcut:`): rolling back a copy and edits in `~/.claude.json` goes through a hash check and will almost always refuse while Claude Code is rewriting the file (the rollback has to be done immediately, or the write moved to the trash); the comment on the write indent may end up after the entry when DeepSeek is moved to the trash and restored; restoring DeepSeek from the trash does not check that `serverName` matches an entry placed in the meantime. **Not verified:** the shape of remote MCP entries (`url` or `serverUrl`) in Antigravity and Claude Desktop against the documentation, so copying such entries may produce a non-working entry at the recipient. The dry run on a real machine: it does not compare `~/.claude.json` byte by byte (the session's own file is rewritten constantly, and the earlier comparison passed by luck); it checks instead that no temporary write files remain.

**Adding an MCP (`Intent::Add`, R2).** In the header there is an "Add MCP" button and a palette item: client (Claude Code, Claude Desktop, Antigravity, Codex; DeepSeek is not allowed, YAML with tags), name, local server (command, arguments, env) or remote (an `http(s)://` address). The same §5 pipeline: preview (env names, no values), hash lock, backup, journal, rollback. The core checks the name (`[A-Za-z0-9._-]`, up to 64), exactly one of `command`/`url`, the shape of env, and refuses if the client already has an entry with that name. A remote server (`url`) is added only to Claude Code (`type: http`) and Codex: the shape in Desktop and Antigravity has not been verified (the Antigravity address may be in `serverUrl`), so only local is available there. An address without a host is rejected. Adding is not part of batches and profiles (it has no entry against which a batch verifies steps). Two core checks (`write.rs`: adding in TOML and JSON, refusals) and an e2e scenario; the independent `checker` review found four minor defects (an address without a host, a pointer with a dot in TOML, a batch with an addition, an echo of the entered env key in the error), all fixed. **There is no package installation:** the window writes the launch line, and `npx`/`uvx` will download the package on the client's first launch. A name with a dot for Codex was verified on a live `codex 0.159.3` (isolated `CODEX_HOME`): `codex mcp add my.server` writes `[mcp_servers."my.server"]`, the same as we do, and shows the entry in `mcp list`. (Codex also replaces the dot with `_` in the tool name for the model, so `a.b` and `a_b` of one client may collide: this is its property, not our refusal.)

**Claude Code plugin installation** ("Install plugin" button, R2): the window calls `claude plugin install <name@marketplace> --scope user` without a shell (`execFile`, name matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}@…`, `-y` is not passed, so plugins that are installed by a marketplace command are rejected by the CLI). First a preview with the exact command, then a separate confirmation; installation without a preview with the same name is refused. This involves the network and third-party code, so the marketplace must already have been added to Claude Code by the owner. Outside the §5 pipeline: Claude Code itself edits the files, no entry goes to the Loadout journal and there is no rollback (to remove a plugin, disable it in the matrix or use `claude plugin uninstall`). The e2e checks the call with a stub `claude`; the real CLI with the network was not run. Other clients: Codex, Antigravity and Desktop have no documented plugin-installation CLI and are not included in the app. `shortcut:` rolling back an addition in `~/.claude.json` goes through a hash check and will usually refuse while Claude Code is rewriting the file; the inverse operation (removing an entry) has not been implemented.

**Plugins and MCP in the matrix are separated** into different groups and rows (`aggregate.ts`): previously one logical key merged a plugin and an MCP of the same name into one row.

**Two UI languages (RU/EN).** A string is written as a pair at the point of use: `t('русский', 'english')` in the window and main (`app/src/shared/i18n.ts`), the `tr!("русский", "english")` macro in the core (`crates/loadout-core/src/i18n.rs`). The core language is one per process (`loadout serve --lang ru|en`, default `ru`) and is never switched inside tests; changing the language in the window restarts the core with the new `--lang` and recreates the window tree. The default follows the system locale (`ru*` is Russian, anything else English); the choice is kept in `settings.json` next to the write level; `LOADOUT_LANG` is for development and e2e only. Branching on Russian text is gone (the trash button label is chosen by the structured field `Plan.trash`). Module-level labels are computed by functions, not at import. The language of ctxkit hooks (`ctxkit setup --lang`) is a separate setting of the installed hooks and does not depend on the window language; `ctxkit doctor` receives the window language. e2e runs the Russian scenarios with `LOADOUT_LANG=ru`, then an English pass: every section, dialogs, a core plan and a core error, not a single Cyrillic letter in text or attributes, and the switch there and back. Journal: the `from`/`to` texts are stored in the manifest in the language of the operation, but when shown, standard words and prefixes ("enabled", "in Loadout trash", "no entry", "copy: ", "add: ") are translated to the current language (`relang` in `write.rs`); a command typed by the user is not translated. A language change is refused while a write or an install is in progress (it stops the core) and it resets the protocol-version check of the new process. The hook grid scrolls horizontally (there can be more events than fit). **Limits:** the core has one request queue, so a burst of requests that arrives before a file event is legitimately handled before it (`MAX_WAIT` bounds the delay of a rescan under a continuous stream, not under a burst); the `request_flood_…` test now feeds heavy requests evenly rather than in a burst. Not verified: the first launch of the packaged build on an English system locale, the text of the OS dialog for raising the level in English, and uninstall through the uninstaller.

### 10.8 Built-in ctxkit (installation, application, effectiveness)

**Design.** The ctxkit binary is built from the `crates/ctxkit` crate of this same workspace and placed in `app/build/ctxkit.exe` (`npm run bundle:ctxkit`, which `pack` and `dist` also call; the source is `CTXKIT_BIN` or `target/release/ctxkit.exe`), from where `electron-builder` takes it into `resources/ctxkit.exe`. main launches **only this** binary by a hard-coded path (`execFile`, no shell, timeouts 20–120 s); third-party copies (`~/.claude/hooks/ctxkit.exe`, `~/.local/bin/ctxkit.exe`) are not launched, only compared byte by byte with the built-in one (matches, differs, absent). The "ctxkit" section (key 7).

**Installation and application.** `ctxkit setup` itself copies the current binary to `~/.claude/hooks` (the path from the hooks) and `~/.local/bin` and writes the hooks and settings, so "install" and "update" are the same command, and the hooks path stays stable even if the app is reinstalled. The form: Claude Code always; checkboxes "rules block in CLAUDE.md", Claude Desktop, Antigravity, DeepSeek Harness; language, advisor model. The page passes only boolean values and enumerations (`parseSetupOptions`); not a single path or arbitrary string gets into the arguments. The **preview** (`setup --dry-run`) writes nothing and is available at any level; **applying** requires R2 and a preview with exactly the same settings (checked by main, not by the page: without it, a refusal even on a direct IPC call). The ctxkit output is shown as text, with the home directory path replaced by `~`. ctxkit makes its own backups itself (`~/.claude/backups`). If Claude Desktop is running, ctxkit with the Desktop checkbox skips the write and warns by itself.

**Diagnostics and effectiveness.** `doctor --json` is shown as a list of findings (ok, informational, warning, error, with a word, not only color) with a hint on how to fix it. `report --json --days 7|14|30` provides counters from Claude Code transcripts: main-session turns by model (share of Sonnet/Haiku and Opus/Fable), subagent turns, advisor and agent calls, the volume of tool results (including file reads and shell inspection), the number of stopped reads, the calls and volume of `ctxkit check`; by day with a model bar. Responses are parsed by shape (`schema: 1`, `tool: ctxkit`), a foreign contract version is rejected, agent keys (written by the model) are truncated by their form. **An honest caveat, in the window itself and here:** the report has no "before ctxkit" baseline, so "saved" is not computed; the effect is visible as the dynamics of the shares and of stopped reads by day after application.

**Checks.** vitest (parsing and arguments, shares and segments, 8 tests); e2e on a copy of the fixture with stub transcripts: version, status "none", applying unavailable without a preview, main refusal on a direct call (without a preview, wrong language, at R0), the preview changes nothing (`settings.json` hash), changing settings invalidates the preview, applying installs the binary, writes the hooks and makes a backup, the status becomes "matches", diagnostics and the per-day table, axe, no horizontal scroll. In development and checks (`LOADOUT_HOME`) ctxkit works in this directory (`--profile`, `--desktop-file`, `--agy-file`, `--dsh-home`), the real profile is not touched; on the packed build only reading was verified against the real profile (version, 6 findings, a 14-day report), and `setup` was not run against the real profile. Screenshots `state/m5-ctxkit-*.png`.

**`checker` audit of the embedding (last round).** It found no data loss and no writes to the real profile (from the `setup.rs` code: all write places go to the passed paths, with `--profile` the copy in `~/.local/bin` is disabled, `--dry-run`, `doctor` and `report` write nothing). Fixed: (1) a write could be sent to a restarted core without a version check (the request waited in the queue during the restart) — now the verified "generation" of the process is bound to the write request and it is not sent to a restarted core; (2) `ctxkit:setup`: one preview is consumed before launch, a parallel second launch is rejected, and on apply `--skip-version-check` is passed (ctxkit checks the `claude` version only after the write, and a hung `claude` would leave the window with an error while the files are changed); (3) `doctor` findings go through the home-path-to-`~` replacement; (4) the dialog backdrop does not drag the window as a title bar; `e2e` checks for the presence of the built-in binary. In addition, after the question of whether the e2e touched the real profile: timestamps confirmed that it did not, and `--claude-json` was added to the isolation (ctxkit read `~/.claude.json` for diagnostics) and the e2e now compares the hashes of the real files that `setup` writes and the number of real backups before and after. **Not fixed:** the trash may contain a hidden copy that the window does not show while the entry is alive in the file (the data is intact in `backups/trash/<id>.json`, with no way out through the window); DeepSeek entries moved out by the build before the audit fixes cannot be restored without an anchor in the trash; the anchor is returned only in the reverse order of removal; `rollback_batch` checks the level even for already rolled-back participants and, on a failure in the middle of a batch, loses the list of rollbacks already done; one invalid day in the report brings down the whole report, huge sums give "Infinity"; the message about `~/.claude/backups` is correct only for Claude Code (for other clients the copies are next to the files); `bundle-ctxkit` takes the working tree of the neighboring repository together with uncommitted edits; ctxkit honors `CLAUDE_CONFIG_DIR` and `DSH_HOME` from the environment, but the status of the copies is computed against the default profile; `run()` and `status()` are not covered by tests.

**Not done.** Removing ctxkit from clients (ctxkit has no rollback command: it can be restored from its backups in `~/.claude/backups`, Loadout cannot do this); switching the language and model without applying again; "before and after" as a separate marker of the start of ctxkit work (the report has none); choosing a Claude Code profile (`--profile`, `CLAUDE_CONFIG_DIR`): the window works with the default profile. The ctxkit version in the app is the one built from the repository at packaging time: a mismatch with the one installed on the user's machine shows the status "different version".

## 11. Risks and open questions

- **The formats are unofficial.** Any client update may change them. Mitigation: adapter version, `unknown` instead of crashing, golden tests.
- **The client will overwrite our file.** For this there is a process check and optimistic locking; the race cannot be ruled out completely.
- **DeepSeek harness:** the format is parsed (§2), but the `cordis.patch.yml` entries show no "disabled" flag: there is only `reconnect.enabled`. So "disable" for dsh most likely means removing the entry from the file. Loadout puts a copy of it into its Loadout trash and restores it on enable. The `dsh-mcp-client` schema was obtained in M1 by downloading the public package (`npm pack` into an isolated directory, nothing was run): the entry really has no "disabled" flag (§10.2). Locally, the dsh packages in `~/.dsh/profiles/node_modules/@deepseek-ai` are junctions into `AppData\Local\npm-cache\_npx\…`, and the target of the `dsh-mcp-client` junction does not exist on the owner's machine (the link is broken). A broken junction is a ready-made `broken` state for the Doctor (not implemented yet).
- **The `cordis.patch.yml` file is written by many tools.** Next to it lie backups from `glidehand`, `sparehand`, `netatlas`, `rea`, `orca`: the installers of these tools edit the file themselves. This means the write race is real, optimistic locking by hash (§5) is mandatory, and the YAML format with the `!!js` tag must not be rewritten as a whole. Edits are made only point-wise, on the text.
- **ChatGPT desktop:** on this machine it is the `OpenAI.Codex` application (§2).
- **`antigravity/mcp/*/*.json`:** possibly a schema cache rather than a config. We never write to it.
- **Copying an entry between clients** (M4) requires format translation (for example, MCP from JSON to TOML). For hooks the event semantics differ, so we carry over only the matching events and honestly show the losses.

## 13. Integration with ctxkit (`crates/ctxkit`)

**The repositories are merged (owner's decision).** The main project is Loadout; ctxkit is now the `crates/ctxkit` crate in the same Cargo workspace (its commit history is preserved by a subtree merge; the former `main` branch of the GitHub repository `d-ridelman/ctxkit` is an ancestor of the new one; the repository was renamed to `d-ridelman/Loadout` and remains private). The shared `Cargo.lock` and `target/` are at the root; the `release` profile (lto, strip) was moved to the workspace root; `install.ps1`/`install.sh`, the `guard.test.mjs` test and `bundle-ctxkit.mjs` take the binary from the root `target/release` rather than from a neighboring repository. The rest of the section was written before the merge and speaks of ctxkit as a neighboring project.

**What is known from the ctxkit code and README (read, not run).** One native Rust binary for the same clients (Claude Code, Claude Desktop, Antigravity, DeepSeek Harness): the `guard` and `backslash` hooks, `ctxkit check`, `ctxkit setup`, `ctxkit doctor` and `ctxkit report`. The last two commands print JSON with `"schema": 1`, and the README says outright "for shells like Loadout". `setup` writes to the same files as Loadout (`settings.json`, `CLAUDE.md`, `ccd-session-presets.json`, `hooks.json`, `cordis.patch.yml`), with a copy in `backups/<name>.<time>.bak`, and refuses to work while Claude Desktop is running (it overwrites the presets). Loadout already sees the ctxkit hooks: the `ctxkit` label in the hook pipeline for Claude Code, Antigravity and DeepSeek.

**Three ways to integrate.**
- **A. Loadout reads ctxkit.** A "Ask ctxkit" button in the Doctor: the window runs `ctxkit doctor --json` at a fixed path (`%USERPROFILE%\.local\bin\ctxkit.exe`, 5 s timeout, the response is checked for shape, `schema` must be 1) and adds its findings ("subagents are not invoked: hook, model, agents, rules block") to its own; `report --json` provides counters for the Radar. Running a foreign binary only on an explicit button press, like the MCP check (§5). There is no code-level coupling; this is the cheapest path.
- **B. ctxkit uses `loadout-core`.** The core depends on neither Electron nor the window (a library crate, the model and scanner of five clients, a safe write pipeline with hash lock, backup, atomic write and journal, which has passed two independent audits). ctxkit could take "what is installed in the client" from it instead of its own config reads, and the shared write pipeline instead of its own backup code in `setup.rs` (1787 lines). This needs a git dependency between repositories and compatible licenses (Loadout is currently `UNLICENSED`, ctxkit has a `LICENSE`).
- **C. A `ctxkit loadout scan|serve` subcommand** in the same binary. A single installation artifact, but ctxkit stops being "one small binary" and pulls in all the core dependencies (`notify`, `yaml-rust2`, `toml_edit`, `jsonc-parser`).

**Owner's decision (after the first version of this section): ctxkit is built into the application**, so that the user can install it, apply it and see the effect (§10.8). This is option A, reinforced by the ctxkit binary shipping directly inside the application (`resources/ctxkit.exe`): Loadout runs exactly that one, not whatever happens to be in PATH. B (shared crate) and C (subcommand) are left for later.

**Initial recommendation:** A after M5, B later, once the write pipeline settles; do not do C. The race between two writers (`ctxkit setup` and Loadout edit the same `settings.json`) is already closed by Loadout's existing hash lock: a write with a stale hash is refused, and the file watcher shows the ctxkit edit as an ordinary change.

**Groundwork done in advance.** The `serve` protocol version (`"protocol": 1`) in `ready` and `status`: the shell (window, ctxkit) checks it and does not work with an incompatible core; the core and the `loadout` binary do not depend on the window; the binary names differ (`loadout`, `ctxkit`), the backup directories differ (`%APPDATA%\Loadout\backups` and ctxkit's `backups/`): they do not overwrite each other's files. The mark and the title line (§10.9) are not tied to ctxkit.

**Open question to the owner.** I understood "add ctxkit to the program" as integration A/B. If something else was meant (for example, putting the Loadout application itself into the ctxkit repository or making it part of the ctxkit installer), the decision changes: then first of all the licenses and the build directory must be agreed on, and A and B are left for later.
